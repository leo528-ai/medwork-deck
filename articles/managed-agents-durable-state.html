长任务 Agent 的状态，不能和容器一起消失

读 Anthropic《Scaling Managed Agents: Decoupling the brain from the hands》

胡浩源｜京东健康 AI 副总裁

一个 Agent 跑到第三小时，容器突然退出。此时最重要的问题不是“多久能重新启动”，而是：前面确认的要求、已完成的操作和仍待处理的问题，还在不在？

Anthropic 这篇文章的答案很直接：不要让任务的生命，依附于某个执行进程的生命。它把 Managed Agents 拆成三部分——保存事件的 Session、调用模型并分派工具的 Harness，以及运行代码的 Sandbox。值得借鉴的不是某个产品接口，而是状态、决策与执行之间的边界。

一、最省事的原型，可能是最难恢复的系统

把一切放进同一个容器，做原型非常方便。文件直接读写，模型循环就在旁边，不必设计跨服务通信。

但原文描述了一个实际问题：容器无响应、事件流丢包、Harness 出错，在外部看起来可能都是“Agent 没动静”。工程师需要进入容器调查，而容器又装着用户数据。故障诊断、安全隔离和任务恢复，被耦合成了一件事。

这类系统的成本不是平时多跑几个毫秒，而是故障发生后必须“抢救那台机器”。它不能随意替换，因为业务状态也困在里面。

我的判断是：长任务系统首先要明确，哪些东西允许丢失，哪些必须持久保存。进程、连接和临时计算可以重建；用户已确认的约束、实际发生的动作和交付记录不能依赖它们。

二、上下文窗口只是工作台，不是档案馆

Managed Agents 将 Session 定义为追加式事件日志。Harness 运行时写入事件；发生故障后，新的 Harness 可以通过 Session 读取历史并继续工作。

这与“把聊天摘要保存一下”不同。

摘要是对历史的选择性压缩。今天看似不重要的一句话，可能成为明天判断某次操作是否合法的关键。如果原始事件已经被删掉，模型再聪明也无法恢复不存在的证据。

原文通过 getEvents() 按位置读取事件片段。Harness 可以回看某个动作之前发生了什么，也可以决定如何压缩、重排或筛选，再送入当前上下文。因此，持久历史和模型此刻看见的内容，是两层不同的对象。

这并不是主张每次把全部历史塞回模型，而是让压缩保持可追溯：工作台可以整理，档案不应随整理一起消失。当然，医疗系统还必须定义保留期限、访问权限及删除规则；“持久”不等于无限期保存一切。

三、拆开执行环境，也是在拆开攻击面

原文把 Sandbox 当作工具调用的目标，而不再让 Harness 住在其中。容器出错，可以作为工具错误反馈；必要时重新配置一个环境。

安全收益更重要。若模型生成的代码与凭证共处一室，一次提示注入就可能诱导代码读取环境中的令牌。仅缩小令牌权限，仍然是在赌攻击者无法利用剩余能力。

文中采用的结构性方向，是让敏感凭证不对生成代码所在的沙箱可见：工具授权由独立机制处理，MCP 的 OAuth 凭证放在安全存储中，通过代理完成调用。

对医疗 Agent，这意味着“允许模型使用某项能力”不等于“把医院系统的密钥交给模型”。身份、患者范围、操作权限和审计，应由执行通道约束，而不是只写在提示词里。

隔离也不是安全终点。代理必须校验每次请求的资源和权限，返回内容仍需防范提示注入；架构减少的是暴露面，而不是取消风险。

四、首字延迟下降，不等于整项任务更快

拆分还允许按需启动容器。无需执行代码的会话，不必先等待仓库克隆、进程启动和环境准备。

Anthropic 报告，其部署中首 token 延迟的 p50 下降约 60%，p95 下降超过 90%。这是特定架构改造后的观测，不是所有 Agent 的通用收益，更不能解读为任务完成时间下降同样比例。

这个区分很重要：用户更早看到回复，是交互改善；最终交付更快、更准确，需要另一套指标。若第一句话很快，后续反复失败，系统仍没有完成价值交付。

五、医疗任务要恢复的，不只是“执行到了哪一行”

以下是我基于原文提出的医疗工程延伸，并非 Anthropic 已验证的临床方案。

一个科研任务可以把状态拆成：研究方案版本、数据版本、代码版本、输出制品、验证结果和人工审批。进程恢复时，先核对这些对象，而不是让模型读一段摘要就继续跑。

更难的是外部副作用。任务已提交，但网络在回执返回前断开，重试可能重复提交。因此，事件日志之外还需要幂等标识、操作回执和外部状态核对。追加式日志不会自动带来“恰好执行一次”。

对于医生已修改的结论，恢复后的 Agent 也不能把它当成普通上下文建议；那是新的权威状态，应覆盖此前的机器草稿，并留下修改依据。

这篇文章真正提醒我们的，是不要把“模型持续运行”当作“业务持续可靠”。模型和 Harness 可以换，容器可以重建，但业务事实、权限边界和验收记录必须有独立的归宿。确定性交付的基础，不是机器永远不坏，而是机器坏了之后，系统仍知道哪些事情确实发生过。
