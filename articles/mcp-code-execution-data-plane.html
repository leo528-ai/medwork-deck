不要让模型当数据搬运工

读 Anthropic《Code execution with MCP》：把编排交给代码，把上下文留给判断

胡浩源｜京东健康 AI 副总裁，医疗专病大模型 & AI 产品线负责人

一个 Agent 查询数据、过滤记录、合并结果、再把它们写入另一个系统。如果每一步都要求模型读完全部结果，再生成下一次工具调用，那么我们其实在用昂贵的语言模型做数据搬运。

Anthropic 关于 MCP 代码执行的文章，指出了一个看似朴素、却很容易被忽视的问题：不是所有经过 Agent 的数据，都应该经过模型的上下文。

MCP 解决的是工具与数据源的连接标准。连接多了之后，另一类问题才开始出现：工具定义占用上下文，中间结果反复进入上下文，多步处理依赖模型一轮轮转述。工具越丰富，Agent 反而可能越重。

一、从“模型逐次调用”，变成“模型编写一段可执行流程”

原文提出，让 Agent 在代码执行环境中使用 MCP 工具。工具能力可以按需发现，数据过滤、循环、组合等操作交给代码执行，而不必把每个中间结果都送回模型。

两种路径的区别可以这样理解：

传统路径：取一批数据 → 模型阅读 → 决定过滤条件 → 再取数据 → 模型合并 → 调用写入工具。

代码路径：模型生成受约束的处理程序 → 程序调用工具、过滤和合并 → 只返回需要判断的结果、异常与摘要。

这里改变的不是“是否使用模型”，而是模型参与工作的层级。它仍负责理解意图和组织操作，但不用亲自充当每一条记录的传送带。

原文给出一个示例：相关上下文从约 150,000 tokens 降到约 2,000 tokens，减少 98.7%。这个数字很醒目，但必须按原文边界理解：它是特定示例中的上下文缩减，不是所有 MCP 任务都能达到的节省比例，也不是准确率提升 98.7%。

二、对于医疗数据，少进上下文还有另一层意义

站在医疗 Agent 的视角，我更关注这种架构对数据边界的影响。

假设一个科研助手需要统计符合条件的病例数量，生成分组结果。最直接的实现，是把大量病例记录传给模型，让它逐条判断、计数。这样既昂贵，也把不必要的敏感信息带入了推理链路。

另一种设计是：由模型生成经过审查的查询和处理计划，在受控数据环境中完成筛选与聚合，只返回脱敏统计、执行状态和需要人工解释的异常。例如：

用户问题
  → 明确纳排标准与数据口径
  → 审核查询计划
  → 在授权环境执行筛选、聚合
  → 返回统计结果、缺失情况和执行记录
  → 模型解释结果，研究者核对

这只是工程推演，不是对某个已上线系统的描述。其关键也不是“用代码就安全”，而是把原始数据所在的位置、模型可以看到的内容，以及对外输出的范围分别控制。

如果程序拥有过宽权限，它完全可能更快地读出不该读取的数据。减少上下文暴露，是可利用的架构优势，不是自动获得的隐私保证。

三、确定性执行，不能替代正确性验证

代码能够稳定执行同一套过滤条件，但条件本身可能错。

例如“最近一次检查”，到底按报告时间、采样时间，还是医生确认时间排序？一段没有语法错误的代码，也可能把缺失值当成零，把多次就诊误合并成一次，把数据不可得解释为临床阴性。

因此，代码执行应至少留下三类证据：输入与版本，实际执行的逻辑，输出和异常。对关键统计，还要设置独立校验，例如样本量守恒、时间范围检查、缺失率检查，以及抽样回看原始记录。

这里可以看到一个重要分工：模型负责提出处理逻辑，程序负责执行，校验器负责检查已知约束，人负责确认研究问题和专业解释。不要因为过程从自然语言变成了代码，就省略后两层。

对长程任务也是如此。程序可以完成循环与重试，但必须明确超时、重试次数和失败返回；不能让一个失败步骤在后台无限重复，最后只给用户一句“正在处理”。

四、把成本从上下文转出去，不是把成本变没了

Anthropic 原文明确提醒，代码执行需要额外的基础设施，包括安全执行环境、资源管理和监控。这个代价应计入整体方案，而不是只展示 token 降幅。

权限隔离、网络出口、依赖版本、临时文件清理和日志脱敏，都会影响落地。一个能够运行任意代码的 Agent，如果没有这些控制，风险面可能大于一组权限有限的固定工具。

因此我不认为所有任务都应改成代码执行。只有一两次简单查询、数据量很小的任务，直接调用工具可能更清楚。复杂数据处理、重复操作和大量中间结果，才更能体现这种架构的价值。

这篇文章最值得借鉴的，并不是某一个节省比例，而是一个系统设计原则：把语言模型留给需要理解、选择和解释的地方，把可以精确表达的处理过程交给程序。

当我们不再要求模型“看见全部、转述全部”，它才有机会把有限的上下文，用在真正重要的判断上。
