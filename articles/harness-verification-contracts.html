ENGINEERING NOTES / ANTHROPIC 工程解读

Agent 说“做完了”之后，真正的工作才开始

读 Anthropic《Harness design for long-running application development》

胡浩源｜京东健康 AI 副总裁

一个音乐制作应用，页面完整，按钮也能变色。点击“录音”，状态显示正在录制。可实际检查后发现，它根本没有采集麦克风。

这是 Anthropic 长程应用开发文章中值得记住的细节。模型不是没有写代码，也不是没有做界面，而是把“看起来有这个功能”误当成了“这个功能真实存在”。

对医疗 Agent 来说，同类问题更隐蔽：生成了统计表，不代表统计方法正确；输出了引用，不代表文献支持结论；完成了整篇报告，也不代表任务通过验收。

一、要分开的不是身份，而是生产与验收

原文介绍的 Harness 将规划、生成和评估分成不同职责。规划者把需求展开，生成者实现功能，评估者检查结果并提出修复要求。

关键不在于有三个 Agent，而在于生成者不能仅凭自己的完成声明决定任务结束。

文章中的迭代约定，将待实现功能与可检验的要求关联。评估并不只读代码，还使用 Playwright 操作页面，结合 API 和数据库检查，判断前端行为与底层状态是否一致。

这给我们的直接启发是：验收必须能穿过展示层。点击“保存”之后，数据是否真的保存？刷新后是否存在？重新进入系统是否还能读取？如果只看按钮和提示文本，模型很容易交付一套“表现正确”的界面，而非正确的业务。

独立评估也不意味着评估者天然可靠。文章仍需要人工校准评分标准。两个模型可能共享同一种盲点，尤其当二者都只看到截图，而看不到外部状态时。

二、验收约定应先于实现，而不是事后补一句“检查一下”

很多 Agent 系统把检查安排在末尾：先完成，再让模型评价。这容易使评估退化为对既有结果的合理化。

更稳妥的做法，是先把成功条件写成可以检查的约定。以科研绘图为例，不能只写“生成生存曲线”，还应确定人群、时间起点、终点事件、删失规则和图表对应的数据版本。

这是本文提出的医疗工程延伸，并非原文的医学实验。

这样的约定需要区分两类内容：允许 Agent 自主选择的实现细节，以及不能擅自改变的研究定义。前者可以自动修复，后者涉及变更就应重新确认。

否则，系统为了通过测试而换了统计口径，表面上消除了错误，实际上却回答了另一个问题。验收标准与实现应分别管理，关键定义不能由同一个执行环节随意改写。

三、长时间运行，只能证明花了资源

原文给出了不同配置的开发案例。在 Opus 4.5 的一个应用任务中，单独运行约 20 分钟、花费约 9 美元；完整 Harness 约运行 6 小时、花费约 200 美元。

这不是同等预算的对照实验。不能据此把全部差异归因于角色拆分，也不能声称 Harness 免费带来了能力提升。更多时间、更多模型调用和更完整的检查，都参与了结果。

另一项 Opus 4.6 音乐应用案例运行约 3 小时 50 分钟，成本约 124.70 美元，但仍有功能缺陷。前面提到的录音按钮，就是“运行足够久”仍不等于“完全做对”的提醒。

我们的评测因此应同时记录完成率、缺陷严重程度、人工修复量、成本和时延。一套系统通过多花十倍资源改善表现，可能对高价值任务很值得，也可能不适合高频小任务。判断应来自业务收益，而不是只看演示震撼程度。

四、模型升级后，有些 Harness 应该删掉

这篇文章最有分量的观点，不是不断给 Agent 加约束，而是重新检查约束存在的理由。

作者曾针对 Sonnet 4.5 接近上下文上限时过早收尾的行为，引入上下文重置。到了 Opus 4.5，相关行为变化后，这层机制可以被移除。随着 Opus 4.6 能力继续提高，原有的部分迭代结构也不再必要。

也就是说，Harness 中的每个组件，都隐含着一个假设：“模型在这里会失败，所以需要这道支撑。”模型变了，假设需要重测。

我的建议是给关键组件建立消融记录：去掉它，哪些任务变差？增加多少错误？节省多少资源？如果只会叠加补丁而不会删除补丁，Harness 最终会成为限制新模型能力的旧流程。

但医疗系统要区分“能力补丁”和“责任边界”。帮助弱模型记住进度的机制可能简化；患者授权、隐私控制、临床审核和审计要求，不会因为模型升级而自动消失。

五、把完成声明变成有证据的状态转换

我更愿意把长程任务的终点设计成一个状态转换，而不是一句自然语言：

执行结束，进入待验收；验证通过，附上输入版本、输出制品和检查结果；涉及关键临床或研究判断，再等待有权限的人确认。缺少任何必要证据，都不能仅凭模型自评进入完成状态。

这里的验证器也必须接受评测。它是否只检查了形式？是否遗漏真实副作用？能否识别一个“按钮正常、功能未实现”的反例？这些问题决定了系统是否只是把自信从生成者转移到了评估者。

Anthropic 的案例属于软件开发，并不证明医疗安全性。但它把问题暴露得足够具体：Agent 的流畅叙述、漂亮界面和长时间运行，都不能代替真实验收。

从医疗工程视角看，确定性交付不是要求模型永远不犯错，而是要求系统不轻易把未经验证的输出宣布为完成。敢于停在“尚未通过”，往往比继续生成一份漂亮结果，更接近专业。
