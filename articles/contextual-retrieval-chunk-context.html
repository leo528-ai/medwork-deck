一段财报为什么检索不到：重读 Anthropic 的 Contextual Retrieval

用户问某家公司一个季度的收入增长情况，知识库里恰好有答案。检索系统却没有找到。

这类问题很容易让人先怀疑 embedding：是不是模型太小，向量维度不够，或者应该再训练一个行业模型？Anthropic 在 2024 年发表的《Introducing Contextual Retrieval》中举了一个更直接的例子。被切出来的段落只剩下“公司收入较上季度增长 3%”，公司名和季度都留在了别处。模型面对的是一句失去身份的信息。

只看这句话，谁也无法可靠地知道它属于哪家公司、哪个报告期。换一个更强的 embedding，未必能补回输入里根本没有的内容。

这篇文章值得重读：它把故障定位到了数据加工环节，并分别测试了向量检索、关键词检索、重排和候选数量，让人能看清每一步的作用。

1. 切块的时候，究竟丢掉了什么

RAG 的常见实现并不复杂。文档被拆成几百个 token 的小块，每块转成向量，查询时找最相似的若干块，再让语言模型据此作答。这样做节省上下文，也让很大的知识库能够被使用。

问题在于，文档里的意义并不总是局限在一个块里。

章节标题可能在前一页；表格的单位写在表头；“上述方法”指向几段以前；公司、年份和产品名称只在文档开头出现。人连续阅读时会把这些信息带过来，切块后的检索系统却未必保留了这种关系。

Anthropic 的财报示例里，问题带着公司名 ACME 和时间 Q2 2023，答案片段只包含收入环比增长 3%。两者应当匹配，但负责区分它与其他公司、其他季度的词已经消失了。

这个例子里至少有两种损失。第一种影响召回：查询包含的实体和时间，在候选文本中找不到。第二种影响回答：即使片段碰巧被找出来，生成模型仍要判断它究竟回答了哪个问题。错误有可能发生在检索之前，也可能发生在检索之后。

我的看法是，排查这类系统时，应当先把查询和实际入库的块放在一起看。如果排查时只检查原始 PDF，看到“材料明明写了”，就可能误以为知识库已经具备回答条件。原始文档有答案，不等于进入索引的检索单元保留了足够的信息。

2. 给每一块补一段针对它的说明

Contextual Retrieval 在文档入库阶段增加了一步：让模型同时看到完整文档和当前块，为当前块写一小段解释，再把解释放到块前面。

如果给一份几十页财报中的每个块都加上同一段公司简介，确实补回了公司名，但营收、现金流、风险披露等段落还是缺少各自的定位。原文提到，他们也试过通用文档摘要，收益很有限；摘要索引的测试表现同样不佳。这是作者在其设置中的观察，不足以否定所有摘要检索方法，但能说明这次设计为什么选择了更细的粒度。

一个针对收入段落的说明，应当让检索器知道它属于哪个主体、哪个时间范围，以及涉及哪类指标。它不需要重新概括整份文档，更不应该抢着回答未来所有可能出现的问题。

原文使用 Claude 3 Haiku 生成这段上下文，通常为 50—100 tokens。输入包括完整文档和目标片段，要求模型只输出简短的定位说明。随后，对“说明＋原始片段”建立向量索引和 BM25 索引。

可以把流程理解为：

原始文档
  ├─ 文档切块
  └─ 完整文档 + 当前块
             ↓
       生成当前块的定位说明
             ↓
       定位说明 + 原始块
          ├─ 向量索引
          └─ BM25 索引

这个设计把额外的语言模型调用放在入库时。文档没有变化，就不需要为每次用户提问重新生成说明。对于重复查询较多的知识库，这种计算位置的选择很重要。

它也引入了一个新的责任：说明是模型生成的，可能写错。把错误时间、实体或范围补进索引，会让检索更积极地找到错误内容。原文没有给出这类上下文生成错误的独立发生率，不能把“加了上下文”理解成已获得事实保证。

实际实现中，我会分别保存原始块、生成说明和来源位置，不把三者揉成一个不可拆分的字符串。检索可以使用合并文本；展示证据和核对事实时，应能回到原始内容。这样既能利用生成说明，也保留了检查它的办法。

3. 为什么还需要 BM25

上下文补全同时服务于两条检索路径。

向量检索适合处理语义接近、表达不同的内容。用户的说法未必和文档一样，embedding 可以帮助跨过这层差异。BM25 则根据词项匹配打分，对标识符、错误码和特定技术名称尤其有用。

原文举了错误码 TS-999 的例子。一个查询可能被向量系统理解为“关于错误代码的技术问题”，召回了一批讨论相近故障的材料，却漏掉真正包含这个编号的页面。词项匹配可以提供另一条路径。

BM25 也不只是数一数单词出现次数。它考虑词在语料中的区分能力、文档长度，并对重复出现的词做饱和处理，避免一个常见词重复很多次就主导排序。

在这套方法里，两条路径都用补过上下文的块：

  • Contextual Embeddings：将补充说明与原始块一起编码为向量。
  • Contextual BM25：对相同的补充文本建立词项索引。
  • 查询时各自产生候选，再通过排序融合、去重得到候选集合。

为什么 BM25 也能从上下文中获益？仍然看财报例子：原块没有公司名，精确词项匹配再好也无从命中。把公司名和报告期补回后，词法检索才有了可匹配的内容。

混合检索的效果仍然取决于入库文本保留了哪些信息。融合之后还需要去重，否则同一块被两条路径找到，可能占掉两个上下文位置。

4. 49% 和 67%，实际测量的是什么

这篇文章最容易被记住的数字是：加入上下文与 BM25 后，检索失败率相对降低 49%；再加入重排，降低 67%。

实验覆盖代码库、小说、ArXiv 论文和科学论文等知识域。主文展示的是采用表现最好的 embedding 配置 Gemini Text 004、取前 20 个块时，各知识域的平均表现。指标是 1 − recall@20，用于描述相关内容未能进入前 20 个检索结果的比例。

主文给出的比较如下：

检索失败率对照，降幅均相对 5.7% 纯向量基线
方案 前 20 个块的检索失败率 相对 5.7% 纯向量基线的降幅
仅向量检索（原始块） 5.7% —
原始块向量检索 + BM25 5.0% —
Contextual Embeddings 3.7% 35%
Contextual Embeddings + Contextual BM25 2.9% 49%
再加入 reranking 1.9% 67%

百分比经过取整，适合看趋势，不应拿来反推未经披露的精确样本计数。

“降低 49%”也不是降低了 49 个百分点。从 5.7% 降到 2.9%，绝对变化是 2.8 个百分点；49% 描述的是相对于原来失败量的降幅。这种改进仍然很有价值，尤其是在大量请求中，但两种说法不能混用。

另一个需要分开的概念是检索质量和回答质量。这个实验直接测量相关材料有没有被召回，不能直接读成“幻觉降低 67%”，更不能读成“任务成功率提升 67%”。

即使所有必要材料都已经进入上下文，生成模型仍可能误读表格、混淆时间、忽略限制条件，或者作出材料没有支持的推断。检索指标解释了错误链条中的一部分，没有覆盖整条链条。

在自己的系统里，我会把这组结果当作值得复现的假设，而不是可直接写进产品承诺的收益。所用模型、切块方式、查询分布以及答案需要多少段证据，都会影响最终结果。这里采用的是 2024 年的实验配置，也不代表今天各 embedding 服务的排名。

5. 重排能筛选候选，但救不了没有召回的证据

原文的重排流程先取前 150 个候选块，再将查询和候选送给 reranker，最后保留 20 个块作为上下文。实际测试使用了 Cohere reranker；文章提到 Voyage 也提供重排服务，但当时没有测试。

这里实际上分配了两种不同的预算。

第一轮检索愿意多拿一些候选，减少过早遗漏。第二轮排序再投入更多计算，比较这些候选与问题的关系。最终送入生成模型的数量受到控制，不必把全部 150 个块都塞进去。

这比“找最相似的 20 块就结束”多了一个判断环节，也带来了额外延迟和费用。减少生成模型处理的内容有机会节省后续成本，但不能据此保证整条请求链一定更快、更便宜；重排本身也要消耗资源。

如果要决定这个步骤值不值得，我会先检查两组失败：

第一组，答案根本不在最初的 150 个候选里。提高重排模型能力解决不了这个问题，应该回到切块、索引、查询和召回阶段。

第二组，答案已在候选中，却没进入最终 20 个块。这才是重排直接负责的部分。

还可能出现第三种情况：相关块确实进入了最终上下文，但它缺少理解所必需的相邻内容。例如只召回结论而没有适用条件。这个问题不一定能通过更精细的单块相关性排序解决，可能需要补回父章节、相邻块或者文档结构。

这些是基于该流程进一步做的工程分析，不能算作 Anthropic 本文已经验证过的全部改进。

6. 每百万 tokens 1.02 美元，不能脱离条件引用

为每个块提供完整文档，会产生明显的重复输入。原文利用 prompt caching 复用同一文档的前缀，从而降低上下文生成的成本。

文章给出的估算是：在 800-token 块、8,000-token 文档、50-token 上下文指令、每块生成 100-token 说明的条件下，生成上下文化块的一次性成本为每百万文档 tokens 1.02 美元。

这是当时模型价格与上述假设下的估算，不是今天的报价，也不是整套 RAG 的总成本。向量化、索引存储、重排、回答生成和后续更新都应另算。

这组假设还有一个很实用的含义：生成工作最好按文档组织，让同一文档的多个块能够复用相同前缀。如果把任务完全打散，缓存命中情况可能改变，实际成本也会偏离估算。

知识库更新频率同样会影响账单。一份更新不频繁、每天被查询很多次的文档，适合在入库时多做一点工作；频繁变化但很少被访问的内容，预处理投入未必划算。某个章节发生变化后，哪些块的说明需要重新生成，也需要有明确的依赖关系。

原文还给出一个更简单的起点：知识库小于约 20 万 tokens 时，可以考虑将全部内容放入提示词，配合缓存使用，而不必立即搭建检索系统。文中提到的缓存延迟与成本收益属于当时的产品说明，不能自动套用到任何任务。

我赞同先比较这个简单基线。小知识库如果内容稳定、访问权限一致，全量上下文可能已经足够。随着文档数量、更新频率和权限差异增长，再引入检索，理由会更清楚。系统复杂度应当对应实际遇到的问题。

7. 真正上线时，需要保留哪些东西

如果据此实现一个知识库，我会让每个检索单元至少能够追溯到以下信息：

chunk_id
document_id
document_version
source_location
original_text
generated_context
context_generator_version
index_version

这是我的实现建议，并非原文规定的数据结构。

original_text 和 generated_context 分开，是为了区分证据与帮助检索的说明。source_location 让人能定位到原文页码、章节或代码行。文档、生成器和索引分别记录版本，则是为了回答一个日常排障问题：为什么昨天能找到，今天找不到了？

如果知识库存在访问控制，权限约束也必须跟随索引单元，并在内容返回给模型以前生效。生成说明可能复述原文中的信息，因此不能因为它是“摘要”就放宽权限。本文的公开实验没有测试企业权限系统，这一点需要实现者自行设计。

对于医学资料，这种区分尤其重要。某段推荐可能受人群、疾病阶段、指南版本或排除条件约束。如果只把一个结论切出来，再由模型补出它“可能适用于谁”，风险会被提前写进索引。

更稳妥的做法是优先保留文档中可以直接定位的标题、版本和适用范围，再让生成说明帮助连接上下文。需要据此执行规则或作出临床判断时，还要回到经过核对的依据。检索优化能够帮助找到材料，不能替代适用性审查。

8. 怎样判断这次改造有没有用

原文提醒读者关注块大小、边界、重叠比例、embedding 选择和上下文生成提示，并建议实际评测。它比较过返回 5、10、20 个块，所报告的设置中 20 个表现最好。

这个结果并不意味着所有应用都应该固定取 20。更多块提高覆盖机会，也可能带入重复内容、干扰信息或相互冲突的版本。如果问题只需一个短事实，20 块可能太多；如果问题必须综合多个章节，20 块也未必够。

要检查自己的系统，我会先固定文档版本和一批有明确证据位置的查询，跑几个可区分贡献的配置：

检索改造的对照评测配置
配置变化 想回答的问题
原始块 → 增加针对性上下文 丢失的上下文是否确实影响召回？
纯向量 → 向量与 BM25 混合 错误是否集中在编号、实体或术语匹配？
无重排 → 有重排 相关材料是否已召回但排名不够靠前？
调整最终块数 覆盖增加是否抵得过噪声和处理成本？

除了汇总 recall，还要保留每条失败查询的检索轨迹。平均值告诉我们整体变好没有，具体失败才能告诉我们下一步该改哪里。对标识符、跨段指代、时间限定和多证据问题分别观察，通常比继续追一个总分更有帮助。

我还会把检索评测与回答评测分开记录。前者检查证据有没有进入候选；后者检查答案是否忠实使用证据、引用能否支持对应结论。这样才能区分“找不到”和“找到了却用错了”。

这篇文章没有公布足以直接套用于所有场景的阈值，也没有在主文里给出临床任务或整个 Agent 的端到端效果。读者拿走的应当是一套可验证的改造路径，而不是一张保证收益的清单。

9. 先检查送进索引的那一小段文字

Contextual Retrieval 最有启发的地方，是把一部分模型计算用在了文档准备阶段。原本需要每次查询时重新猜测的关系，可以先在入库时解释清楚，再接受检索评测。

这条路径也有代价：索引更大，入库更慢，生成说明需要质量控制，文档更新时还要维护一致性。对知识库做一次版本更新，其影响因此不再只是替换文件。

但在升级整套模型之前，有一个成本很低的检查值得先做：拿一条失败的问题，找到它本应命中的原文，然后看看实际入库的块。

如果那个块连自己属于谁、说的是哪一年、适用于什么范围都没有交代清楚，那么问题已经出现在检索模型接手之前。
