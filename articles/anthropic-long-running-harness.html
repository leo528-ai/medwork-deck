医疗 Agent 不能靠“我记得”

读 Anthropic 长任务 Harness：
从会话记忆到可验收的科研执行

胡浩源｜京东健康 AI 副总裁

医疗 Agent 做一次问答，与连续完成一个科研任务，是两类不同的工程问题。

后者可能从讨论研究想法开始，经过方案确认、可执行代码、回顾性数据分析、统计检验和图表生成，最终形成符合模板的交付物。任务跨越多个会话，也跨越不同工具。真正困难的往往不是某一步不会做，而是：下一次启动时，它是否知道哪些已经验证、哪些仍有问题，以及凭什么继续。

Anthropic 在 2025 年 11 月 26 日发布的《Effective harnesses for long-running agents》，讨论的正是这个问题。文章以 Web 应用开发为实验场景，并未验证医疗应用。但从京东健康的医疗 Agent 工程视角看，其中最值得借鉴的不是“让模型运行更久”，而是把长期任务变成有状态、有验收、能恢复的执行过程。

一、上下文压缩，不等于工作交接

原文观察到两种典型失败。

第一种是一次做太多：模型试图直接完成整个应用，在上下文耗尽时留下半成品，下一轮只能猜测上轮做到了哪里。第二种恰好相反：模型看到已有一些功能，就过早宣布任务完成。

即使具备上下文压缩，这些问题也没有自然消失。原因在于，聊天摘要主要回答“之前说了什么”，而任务交接还必须回答：

  • 当前哪个版本可用？
  • 哪些要求尚未满足？
  • 哪些结论经过实际验证？
  • 下一步从哪里开始，失败后退回哪里？

这也是我理解 Harness 的起点：它不只是把模型和工具接起来，而是管理模型工作的状态、约束和验收。

二、原文的关键：初始化一次，每轮只推进一小步

Anthropic 将流程分为初始化和后续编码两个阶段。

初始化阶段建立 init.sh、记录进展的 claude-progress.txt，并创建初始 Git 提交；同时把用户需求展开为结构化功能清单。在复刻 claude.ai 的示例中，这份清单包含 200 多项功能，初始状态全部为 passes: false。

后续每轮先读取进度和 Git 历史，启动环境，检查基本功能是否仍然正常，再选择一个未完成的高优先级功能推进。完成后进行测试，更新进度，并留下描述清楚的 Git 提交。

这里有三个容易被忽略的细节。

第一，默认未通过，而不是默认完成。 功能存在于代码中，不等于已经通过验收。

第二，验收标准不能随实现一起漂移。 原文要求编码 Agent 只能改变清单中的 passes 状态，不能删除或修改测试。使用 JSON 而非 Markdown，是因为作者在实验中发现模型更不容易不当地改写 JSON；这是一项经验观察，不是格式本身提供的安全保证。

第三，先检查基线，再增加功能。 如果上一轮已把环境破坏，新一轮继续开发只会放大问题。Git 历史和进度文件让恢复有据可循，而不是靠模型重新猜一遍。

原文所谓两个 Agent，实际主要是首次用户提示词不同，系统提示词、工具及整体 Harness 相同。它不是多 Agent 协作优于单 Agent 的证明。

三、“代码跑通”离“科研任务完成”还差多远

原文发现，模型即使执行了单元测试或 curl 检查，也可能遗漏端到端问题。因此，它要求模型借助浏览器自动化，像真实用户一样操作应用，并通过 Puppeteer MCP 验证功能。

这对医疗科研的启发是：验收对象必须是完整任务链，而不只是中间代码。

例如，一个回顾性研究任务，不能以“脚本退出码为零”作为完成条件。至少还要检查：

  • 队列是否符合已确认的纳排标准，人数变化是否可解释；
  • 时间窗、指标单位和缺失值处理是否与方案一致；
  • 统计表、图和报告是否引用同一次分析结果；
  • 结果能否追溯到数据版本、代码版本和分析参数。

这不是原文已实现的医疗功能，而是我们可以据此设计的工程扩展。

特别需要防止的是：Agent 为了消除报错，擅自改变纳排标准、替换终点，或者删去“不好处理”的样本。这相当于编码 Agent 为了通过验收而修改测试。系统表面上继续运行，研究问题却已经变了。

所以，科研初始化阶段不应只生成任务清单，还应形成经研究者确认的分析约定。任何实质性变更，都应进入重新审批，而不是被归类为自动修复。

四、为医疗任务补上状态机和人工接管

我建议将原文的“功能是否通过”，扩展成显式的任务状态。下面只是设计示意，并非 Anthropic 原文实现：

待确认 → 可执行 → 执行中 → 待验收 → 已验收
                    ↓         ↓
                   阻塞 ← 验收失败

恢复时：
  读取任务状态、制品版本、验证记录
  检查已验收基线
  若权限不足、定义冲突或数据异常：
    阻塞并请求人工处理
  否则执行一个最小任务单元
  验收通过后记录证据，再推进状态

每个任务单元应绑定输入版本、输出制品、验证结果和未解决问题。状态应由 Harness 根据验证结果和审批记录控制，不能只依赖模型写一句“已完成”。

医疗场景还必须区分“未知”和“否”。病历没有记载某项过敏史，不等于患者无过敏史；某项指标未测量，也不能自动填成正常。这样的未知状态应保留，并触发相应的补充信息或人工判断流程。

恢复也不等于简单重跑。Git 可以帮助恢复代码，却不能撤销已经发送的消息或已提交的外部操作。因此，涉及外部写入时，还需要幂等控制、操作回执和权限边界；影响临床决策的关键环节，必须保留医生审核与接管入口。

五、用 Benchmark 判断系统是否真的进步

这些设计是否有效，不能靠一次演示判断。

我们需要把真实失败转化为固定评测任务：中途打断后能否正确恢复，基线损坏能否被识别，缺失信息会不会被当成否定事实，统计表与报告是否一致，以及该请求人工判断时是否停下。

Benchmark 应成为模型、工具、Skills 和 Harness 共同迭代的客观北极星。系统改进不只来自模型参数更新，也可能来自更好的状态结构、验证器或恢复策略。但任何改动都应接受同一套回归检查，并兼顾成功率、人工介入质量、成本和耗时，避免只优化一个表面分数。

Anthropic 也明确指出，其演示针对全栈 Web 开发，迁移到科研等领域仍是后续方向；浏览器自动化本身也存在观测盲区。因此，我们不能把软件演示直接解释为医疗安全或临床有效性的证据。

这篇文章给我的核心启发是：长任务 Agent 的可靠性，不在于它能连续说多久，而在于每次停下后，系统能否清楚交代：做了什么、如何验证、哪里未知、接下来谁来负责。

医疗 Agent 要走向可信执行，这些问题不能留在模型的“记忆”里，必须进入系统的工程结构中。

原文：Justin Young，Effective harnesses for long-running agents，Anthropic Engineering，2025 年 11 月 26 日。
