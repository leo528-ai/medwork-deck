从第一次建档，到日常选择、反馈纠正与年终回顾。

视频为概念演示，以虚构人物陈晨、示意餐厅与健康记录，呈现个人健康 Agent 的交互设计。

拍下一份午餐，系统告诉你“这是米饭、青菜和鸡肉”，只能算识别的开始。真正有用的下一步，还要知道：你早餐吃了什么，今天在哪里，是否赶时间，上一次建议有没有做到，以及你愿意把哪些信息交给它记住。

一年的时间线串起陈晨的生活：从第一次建立档案，到吃饭、出差、调整习惯、复查和年终回顾。照片、语音、菜单、报告与设备记录并不是几条平行的输入通道，而是在不同时间回答同一个问题：现在怎样帮助这个人，才适合他的真实处境？

一、1 月：先认识陈晨，也让陈晨决定被记住什么

陈晨 38 岁，经常出差，午餐多在食堂解决，不喜欢跑步。他想把日常健康管理做得更有条理，却不希望每天重新介绍自己，也不想被提醒填满生活。

建档不能只是一张等着填完的表。陈晨可以拍体重秤、上传报告，也可以用语音补充“这张照片是昨天的”“最近工作比较忙”。多模态理解把分散的信息转成可确认的记录：数值是什么，单位是什么，发生在什么时候，来自照片还是本人补充。照片看不清的地方要留白，不能靠一个完整的表格掩盖未知。

这时，界面承担着与模型同样重要的工作。演示中的记忆卡将测量事实、个人偏好和生活约束分开，并提供“确认保存／修改／不保存”。待确认的记录与已经确认的记录有所区别，原图和提取结果能够对照；“保存到健康档案”和“允许主动提醒”应当是分别可理解的选择。用户确认一次信息，不意味着同意今后所有用途。

长期记忆从这些小选择开始。“不喜欢跑步”可以影响活动候选，“本周出差”只能在一段时间内有效。陈晨要能查看、纠正和删除它们。个性化并不取决于系统收集了多少信息，而在于它是否记住了合适的信息，并知道什么时候不该继续使用。

二、2 月：从看懂菜单，到记住真正吃下去的那一餐

二月的场景最日常，也最能看出多模态 Agent 与单次识图的差别。早餐已有记录，中午陈晨拍下食堂菜单，系统需要把“今天有哪些菜”与“这个人今天已经吃了什么”放在一起理解。

菜单解决候选是什么，餐盘照片帮助理解搭配，语音补充图片没有的信息。演示中，系统结合早餐记录和“不爱西兰花”的已确认偏好，给出番茄炒蛋、清炒青菜与小份米饭的组合。输出的价值在于帮助陈晨完成眼前这一餐的选择，说明依据，并保留调整空间。

份量、烹调方式和实际吃下去的比例，往往无法从照片可靠确定。因此，界面里的估算应显示依据与不确定性；信息不足时，问一个有用的问题，比给出精确到个位的热量数字更诚实。记录也应允许用户修改份量，而不要求他接受系统的第一次判断。

吃完后，陈晨补充：“米饭只吃了一半。”这句话应该回到原来的午餐记录，修正主食的实际摄入；其他菜吃了多少仍按已有证据记录，不能把整餐统一折半。反馈不能只在聊天末尾留下一个孤立备注。晚餐的下一次建议，应当基于修正后的状态。多模态负责把输入看懂，长期记忆负责把事实接上，反馈闭环负责让下一步真的发生变化。

这也是一个具体的产品验收点：同一餐能不能从“候选”进入“已选择”，再进入“实际吃了多少”；用户能否看出哪些信息是照片识别的，哪些是自己确认的。若这些状态混在一起，再流畅的对话也可能把计划误当成事实。

三、4 月：到了陌生城市，帮助也要跟着处境改变

四月，陈晨出差住进酒店，晚上九点还没吃饭，也不想运动。此时继续催他完成原来的活动计划，没有多少实际意义。Agent 先处理眼前的需要：安排一顿方便吃上的晚饭，再考虑当晚休息与第二天的行程。

演示先呈现位置授权，再依次展示两张示意餐厅卡，说明授权、选择和行动确认怎样衔接。接入真实检索时，候选还需要标明查询时间、距离、价格与营业信息；商家页面里的“健康餐”不能直接变成医学结论，营业状态也要按当时情况核实。

餐厅卡让陈晨逐一查看候选，再自行选择。界面上的距离和营业信息在真实服务中会影响取舍，也应能回到对应来源核对。用户选择之后，计划再随之更新。展示候选不等于替用户下单，获得位置权限也不等于获得交易权限。

这里的个性化不是在餐厅名称旁加上“为你推荐”，而是让帮助随情境改变。陈晨补充“明早七点要出门”，早餐计划便改成便于提前准备的安排；当晚休息，不用补做运动。新的时间约束直接改变了下一步。建议必须能落进日程，才有机会变成行动。

四、6 月：用户纠正系统，是持续服务最有价值的输入

到了六月，系统已经积累了一些历史，但历史不能成为替用户做决定的理由。六月复盘呈现晚餐时间、已有睡眠记录和未完成的活动计划，缺少记录的日子保持未知。陈晨解释：“下班太晚，真的累了。”这是对原计划可行性的纠正，也是在更新当前的生活约束，不能被固化成一个永久标签。

好的体验应当让纠错产生可见的后果：后续候选避开不喜欢的活动，近期计划降低安排密度，提醒时间随授权设置调整。原来晚饭后的活动屡次被加班打断，新的午休十分钟安排进入“记忆更新·待确认”卡片，经本人确认后再替换旧计划；这里的十分钟是日程示例，并非通用运动处方。用户不必靠连续拒绝来训练一个不肯改变的助手，也不需要为没有完成上次计划作出解释。

重规划不只是换一句鼓励的话。系统应保留原计划与新计划的关系，告诉陈晨“因为什么改了什么”，并允许他进一步修改。若反馈来得较晚，也要对应到当时的事件，不能误算成今天完成了一次活动。

这一段强调的闭环很朴素：看到了新情况，就更新事实；约束变了，就重新安排；用户说停，就停止主动推进。长期陪伴的稳定性，不在于每天都坚持发消息，而在于经历中断、纠正和变化之后，系统仍能准确地接着往下做。

五、9 月：复查时，把一年中的零散记录交成一份可核对的材料

九月的复查把视角从日常选择转向信息交接。新的报告到来后，多模态模型可以帮助定位项目、提取数值和单位，再与已有记录建立联系。但名称相似的项目不一定能直接比较，不同时间、单位、检测条件和来源也可能影响解释。

因此，面向医生的交接材料不应只剩一张漂亮趋势图。每个关键结果都需要保留日期、来源和原始报告入口；缺失、冲突或未经确认的记录要明确标出。陈晨的自述、设备测量与模型估算也应能区分，不能被压成同一种确定事实。

这一步真正减轻的是整理负担：把需要带去沟通的材料组织好，把陈晨想问的问题列出来，把相关生活变化放在可读的时间线上。最终的医学解释和处置仍需要专业人员判断，Agent 不应根据一条趋势自行调整药物或承诺风险已经下降。

分享本身也是一次行动。陈晨应当能够预览内容、选择范围，并决定是否交给指定对象。曾经允许系统保存报告，并不自动包含对外发送报告的授权。理解信息、整理信息和分享信息，是相互衔接、权限却不同的三件事。

六、12 月：年度总结，应当总结发生了什么

到年末，最值得呈现的未必是一个总分，而是这一年可被说明的变化：哪些习惯反复被选择，哪些计划做了调整，哪些提醒被关闭，哪些记录得到纠正，还有哪些问题需要在下次沟通时继续确认。

年度回顾应该允许陈晨回到具体事件，而不是把有记录的日子等同于健康改善、把没有记录的日子等同于没有行动。报告里可以看到数据覆盖了哪些时段，也应该能看出空白在哪里。缺失本身是一种信息，不应被补成一条平滑的进步曲线。

即使某个指标发生变化，也不能仅凭同时使用了 Agent，就把变化归因为产品效果。年度总结应分开呈现记录覆盖、计划执行与健康结果，并分别核验：帮助是否更容易理解，信息是否更容易核对，计划是否更能适应生活，用户是否始终保有决定权。

七、真正需要连起来的，是理解、记忆和下一步行动

回看这一年，单个模型能力都不陌生：识图、语音理解、检索、生成与工具调用。难的是让它们围绕同一个人协作，又不把识别结果当成事实、把偏好当成永久规则、把建议当成已经完成的行动。

多模态让陈晨用自然的方式表达处境；个性化让系统少重复无关建议；长期记忆让过去的信息在恰当的时候被找回；执行反馈让今天的结果改变明天的安排。任何一层断开，产品都容易退回到“每次聊得不错，每次又从头开始”。

持续的帮助，需要把每次输入纳入下一步行动的判断。技术上怎样保存有来源的事件，怎样处理记忆修正、证据检索、计划版本和授权执行，可以继续阅读《MedWork 健康管理 Personal Agent 的实现》。应用体验与工程设计，应当在同一条闭环上互相验证。
