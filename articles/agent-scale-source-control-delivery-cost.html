01｜先看交付的队列，再看生成的速度

一个编码 Agent 十分钟完成修改，流水线却用四十分钟准备环境，再用二十分钟等待检查。此时继续提高生成速度，用户未必更早拿到结果。更麻烦的是，便宜的生成会鼓励更多并行尝试：分支更多，测试更多，下载也更多。原来不起眼的固定开销，会被任务数量反复放大。

Anthropic 10 月 13 日发布、15 日更新的 Scion 案例给出了一个鲜明信号：日均合并从 5 月约 2,500 次升至 9 月超过 30,000 次；新系统采用在线客户端、服务端操作、增量变更和分层缓存。其自报 CPU、内存需求降至旧 Git 镜像设施的约 1/200，CI 获得 25% CPU 容量收益。作者明确说它不适合作为通用 Git 替代品。原文

这些数字说明了工作负载的特殊性，不能直接变成任何团队的采购回报率。本文接下来讨论的是我的工程判断：面对不断增加的 Agent，如何测量瓶颈、选择数据粒度、设计缓存与发布约束，以及怎样决定要不要改造。下面的算例均为假设，不是 Anthropic 的额外实验，也不是我们的线上成绩。

首先应把一次任务的总时间拆开：排队、拉取源代码、准备依赖、推理、编辑、测试、人工审阅、发布。最好再记录各阶段占用的 CPU 时间与传输字节。等待很长未必计算很贵，传输很少也未必等待很短。把这些量混成一个“任务耗时”，会让优化方向变得模糊。

假设原任务共需六十分钟，其中生成占十分钟，其余五十分钟完全不变。把生成速度翻倍，任务变成五十五分钟，整体用时只缩短约 8.3%。这是简单的时间分解，不需要假定任何特定模型。若团队只报告生成步骤快了一倍，却不报告交付时间，很容易把局部能力错当成产品收益。

我的第一张看板会展示任务总时长的分位数、各阶段贡献以及失败重跑次数。中位数描述日常体验，长尾揭示拥塞与冷启动。真正需要回答的是：多增加一倍有效任务时，哪个共享组件最先让所有人等待？

02｜一次小修改，为什么会搬运一个大仓库

考虑一个假想仓库：完整工作副本为 10 GB，一项任务实际读取 150 MB。若每天启动 10 万个任务，且每次都独立下载完整副本，不考虑压缩和复用，传输量就是 1 PB；实际读取集合合计只有 15 TB。这个约 67 倍差距只是一个“全量下载”上界算例，真实系统必须用采样数据测量，不能拿它当节省承诺。

这个算例把问题落在读取放大上：为完成一次任务，系统移动了多少数据，其中多少真正进入了文件读取、编译或测试？下载量、磁盘落盘量和实际读取量应分别记录。若 Agent 只查询某文件最后修改者，却先准备整个工作区，浪费发生在接口边界，未必发生在网络设备。

但也不能只凭第一分钟的读取行为决定最终所需目录。测试可能动态加载资源，构建脚本可能扫描项目根目录，代码生成器可能依赖另一个包。一次稀疏检出能成功启动，不等于任务整个生命周期都不再补取文件。应观察任务结束时的累计工作集，而不是只看首屏速度。

我会把任务分成三类：只问仓库元数据的查询；需要少量文件的编辑或分析；需要完整依赖闭包的构建与集成测试。这三个群体不该默认使用同一种准备方式。第一类可能通过查询服务完成，第二类适合按任务取文件，第三类则需要较强的依赖发现和制品复用。

这里的判断标准也不是“谁下载最少谁最好”。如果文件需求过碎，每次读取都引入一次高延迟请求，少传数据反而更慢。批量请求、邻近文件预取和并发上限，需要围绕真实访问轨迹调节。优化目标应是完成任务的总成本，同时满足延迟和可靠性要求。

03｜先用好已有能力，再讨论更换版本系统

Git 已有不同层次的裁剪能力：shallow clone 用深度约束历史，partial clone 通过对象过滤推迟传输，例如 blob:none 把文件内容留到需要时获取。它们裁剪的对象不同。git-clone 官方说明

sparse checkout 则控制工作树中出现哪些路径；cone 模式以目录集合表达范围。官方文档还提醒，相关命令与工具兼容性需要注意，merge 或 rebase 可能为了处理冲突而物化额外文件。git-sparse-checkout 官方说明

所以我不会把“浅克隆”“稀疏目录”“按需对象”当成同一个开关。一个团队可能只缩短了提交历史，却仍下载大量当前文件；也可能只隐藏了工作树路径，但对象已经传输到本地。看工作区大小不能替代网络测量，看 clone 成功也不能替代后续命令测试。

试点时，可以固定一个代表性提交，分别跑原流程、仅减少历史、仅减少工作目录、两者与对象过滤的组合。每组都要执行相同任务，而不只是比较初始化。检查 diff、历史追溯、版本计算、构建和失败诊断是否仍然成立。若某一步偷偷回源下载了完整对象，前面的收益可能只是转移了发生时间。

再看兼容性成本。某个老插件若默认历史完整，可能给出错误版本号而不是明显报错。这样的静默错误比慢几秒更值得防范。为裁剪方案建立小型兼容性测试集，应包含历史不足、目录缺失、跨包修改和合并冲突，而不是只覆盖无冲突的单文件修改。

对多数没有测到严重瓶颈的团队，先减少重复工作更稳妥。新版本系统的成本不是一个服务器，而是开发者工具、权限、审阅、CI、审计、恢复及供应商生态的整体迁移。只有旧系统的真实限制已经形成持续损失，而且渐进优化不足，才值得把这笔迁移账摊开。

04｜把不可变内容和可变判断分开

Git 自身就采用内容寻址的对象存储：内容生成键，之后可通过键读取对象。这个基本结构并不属于某个新系统独有。Pro Git：Git Objects

从这个基础出发，可以设计一套通用的任务数据接口。先让任务绑定明确的修订标识，再读取该修订下的路径和对象。这样，任务读到的是一组确定版本，而不是在长时间执行过程中不断漂移的“最新文件”。下列是接口草图，不是某家公司公开的 API：

resolve_revision(repository, reference) → revision_id
list_paths(repository, revision_id, prefix) → paths
read_object(repository, object_id) → bytes
query_changes(repository, base_id, revision_id) → changes

这里最重要的是 reference 与 revision_id 的区别。前者可能随着合并前进，后者标识任务选定的输入。若每次文件读取都重新解析 main，任务就可能拼出一个从未存在过的混合工作区。即使每个文件都合法、每次网络请求都成功，组合结果也不一定能复现。

其次要区分原始记录与派生查询。文件内容、提交关系可以作为底层事实；影响范围、路径历史、代码归属等查询，可以由索引加速。但索引需要版本和就绪状态。更新已落盘而索引还在追赶时，系统应说“查询暂不可用”，而不是用空结果暗示没有变更。

我会让查询响应带上输入修订、索引版本和完整性标记。对于关键问题，宁可显式等待或使用受控慢路径，也不要悄悄返回陈旧答案。索引升级也应支持影子比较：同一批问题同时询问旧实现与新实现，记录差异，再决定能否切换。

把内容留在对象层，把理解内容所需的索引留在查询层，可以降低很多无谓的文件准备。但服务化之后，权限检查、超时、配额和可观测性也集中到了接口上。少维护一个本地仓库，不代表少承担一份系统责任。

05｜高命中率的缓存，也可能是故障放大器

假设一个任务集群每秒发出 10 万次对象请求，正常情况下 99% 在缓存层命中，源站每秒承受 1,000 次。若命中率暂时降到 95%，源站流量就变成每秒 5,000 次，即五倍。这个算例说明：命中率只降低了四个百分点，源站压力可能发生数量级上重要的变化。它不是任何公司的实测数据。

因此，“平时命中率很高”不足以证明架构安全。发布大版本、扩大集群、迁移区域、驱逐缓存，都可能让大量任务同时请求尚未预热的对象。真正需要压测的是缓存失效时系统如何退化，尤其是上游是否会被重试风暴压垮。

我的设计顺序会是：先定义源站可承受的预算，再决定缓存允许的回源并发；同一对象的重复请求应尽可能合并；失败重试需要抖动与次数限制；超过预算时应排队、降级或拒绝新任务，而不是无限向上游转发。对可重新调度的 Agent 任务，晚几分钟开始通常优于把共享服务一起打倒。

缓存还涉及隔离。内容哈希可以帮助判断对象身份，却不能单独证明调用方有权读取它。哪怕两个项目恰好包含相同字节，也不能据此跨越租户或目录权限边界。缓存命中路径与源站路径必须执行相容的授权策略，不能把“已经有人下载过”当成新的授权。

有些数据适合长时间缓存，有些不适合。例如固定对象的字节内容相对稳定，而分支指向、访问权限和撤回状态可能变化。把它们用同一套失效规则处理，会在性能与安全之间制造隐患。设计前先列清对象的可变性和权限语义，比选一个更快的缓存产品更重要。

验收时可以直接构造三个故障：一个区域缓存不可用，热门对象刚被替换为新版本，大批任务同时冷启动。观察源站请求量、排队时长、失败比例和恢复后的积压消化速度。只有这些曲线受控，高命中率才是一项可信的收益。

06｜写入内容很快，不代表发布状态可以乱序

并行 Agent 往往可以独立产生候选修改，但最终哪些修改成为当前版本，仍然涉及共享状态。这个边界不能靠“所有操作都做成无锁”一笔带过。更好的问题是：哪些步骤可以独立完成，哪些步骤必须明确发生顺序？

考虑两个任务 A、B，均从修订 R0 出发。A 增加字段，B 修改读取逻辑。它们各自保存候选结果可以并行；但若两者都无条件把 main 设为自己的结果，后一次更新可能覆盖前一次。常见的处理思路是带预期版本的条件更新：只有当前指向仍是 R0，才允许发布该候选。预期失效时重新基于新状态处理，而不是静默覆盖。

# 设计示意，并非可直接用于生产的事务实现
candidate = save_candidate(base_revision, patch)
result = advance_reference(
    expected_revision=base_revision,
    proposed_revision=candidate,
    approval=verified_approval,
)
if result == "base_changed":
    return revalidate_against_current_revision()

这段草图故意没有把“保存候选”与“允许发布”合并。候选可以很多，发布权必须清楚。还要处理响应丢失：服务端已经成功，客户端却因为超时认为失败。若直接再做一次，就可能出现重复副作用。任务需要稳定操作标识，并能查询前一次操作结果。

同样，批准记录应绑定被审阅的内容，而不是只绑定一个会继续变化的分支名字。若审阅后又产生新修改，原批准能否继续适用，必须有明确规则。把审阅、测试和发布三种证据都绑到不可变候选上，才能知道“通过检查的究竟是哪一份”。

这是我认为 Agent 平台最容易低估的一笔成本：生成候选是局部过程，发布候选是系统承诺。前者能弹性扩容，不意味着后者可以省略一致性、授权、幂等和审计。

07｜CI 需要证明的，是组合之后的状态

GitHub 的合并队列会把候选变更放到目标分支最新状态及队列中更早变更之上，运行所需检查。官方文档还要求 CI 正确响应 merge_group，否则可能等不到必要检查结果。GitHub 合并队列文档

这个机制回应了一个基本问题：A 单独通过，B 单独通过，不代表 A+B 通过。Agent 只是让这类组合更频繁发生。把“模型能更快修复”当作取消所有前置检查的理由，等于把检测和恢复成本转嫁给其他开发者，甚至生产用户。

可以用一个假设估计版本漂移的规模：若每分钟合并十个修改，而一次集成测试需要二十分钟，测试期间可能有约两百个修改进入主线。这不表示一定冲突，但说明测试结果必须绑定具体快照。一个写着“绿色”的标记，如果没有修订和环境信息，几乎无法用于发布判断。

不同团队可以选择不同的控制策略。影响范围清楚的修改可以分组验证；共享依赖变化需要更广的回归；风险较低的候选可以先进入隔离分支；发布前仍应验证实际准备上线的组合。关键是把允许的风险写成规则，而不是用“我们有 Agent 修复”代替规则。

更激进的后置验证，需要额外条件：能快速定位引入问题的变更，能安全回滚，能阻止坏状态进入生产，而且失败影响有边界。只要其中一项缺失，减少合并前等待就可能增加更昂贵的恢复时间。不能只比较成功路径的吞吐量。

我会把 CI 分成快速反馈、组合验证、部署放行三层。第一层尽早帮作者发现低成本错误；第二层评估共享状态；第三层负责真正的上线承诺。这不是固定产品配置，而是职责划分。某些检查可以复用，但每层究竟证明了什么，需要在结果里明确写出来。

08｜改造应有退出路径，而不是一次性押注

如果决定建设服务端查询层，我会先选一个只读问题，例如“这个候选影响了哪些目录”。旧流程继续作为真实工作路径，新接口只做影子计算，比较返回结果、延迟和资源消耗。这样能验证数据模型，又不必马上迁移开发者日常操作。

下一步是挑一个低风险任务族，例如只生成静态报告的分析任务，让它使用新接口。明确失败回退策略和流量上限，避免新系统有问题时所有任务同时逃回旧系统，反而压垮旧系统。回退也要有容量预算。

然后才测试稀疏工作区、共享对象缓存与更广的任务范围。每增加一种能力，都保留独立验收：内容完整性、修订一致性、权限边界、冷启动表现、长尾延迟。不要把四种变化一次上线，再用整体收益掩盖其中某一项退步。

迁移过程里有一个容易被忽略的资产：可重放的任务样本。样本应包含目标修订、任务类型、预期读取集合、操作序列和期望结果，不必包含生产秘密。对于依赖仓库历史的任务，还要覆盖分支删除、重命名、合并父节点和历史不完整等情况。

写路径最后迁移。需要先证明旧系统与新系统对提交、授权和当前状态的理解一致，再逐步扩大发布范围。对双写要尤其谨慎：如果两边成功条件不同，就会出现两个都声称权威的状态。应有明确主从关系、对账方案和切换条件，不能只靠操作人员记住哪个系统更新了。

一个值得批准的迁移方案，应能回答：如果明天停止项目，已经完成的哪一部分仍有价值？只读 API、任务遥测和兼容性测试通常可以保留。若所有收益都依赖最后一天彻底替换整个开发体系，项目风险就应被如实计入。

09｜用完整账本判断，而不是只挑一个漂亮倍率

基础设施文章常有引人注目的倍率，但团队自己的决策要看完整账本。哪项资源下降了，哪项成本转移到数据库、对象存储、网络或运维？从开发者机器节省的等待时间，是否对应实际可利用的计算容量？这些问题没有一个倍率能够代答。

我会在试点报告里使用以下表格。所有行都是验收建议，没有预填收益，也不冒充已完成的实验。

检查项需要记录必须同时核对
任务准备冷、热启动分位耗时后续补取是否把延迟移走
数据搬运传输、落盘、实际读取字节压缩与跨任务复用口径
查询正确性新旧实现差异及索引延迟缺失结果是否被误当成空结果
故障恢复失效时源站负载、积压和恢复时间重试是否放大故障
交付质量回退率、坏构建、发布事故任务量及难度是否改变
总成本计算、存储、传输、维护与迁移投入收益是否只存在于局部组件

测试必须固定任务分布。若新系统主要接收简单任务，旧系统继续承受困难任务，平均值自然会好看；这不是同条件比较。可以先重放同一批任务，再做受控分流，按任务类别比较，并保留失败与超时，而不是只统计成功样本。

还要记录需求反弹。一次任务更便宜以后，业务可能启动更多尝试，总账单未必下降。若这些新增尝试带来更多有效结果，那可能仍然值得；若只是生成了更多无人审阅的分支，节省可能被无效工作吞掉。最终指标应接近每个被采用结果的成本，而不只是每次 API 请求的成本。

技术团队也需要给维护工作定价。一个特殊架构在成熟期可能很高效，但它会要求长期拥有数据迁移、故障恢复和权限模型的知识。不能只比较第一周运行账单，而忽略未来几年谁负责排障、升级和兼容。

10｜把更快生成的代码，变成更快兑现的结果

从这次阅读中，我得到的判断是：Agent 能力的增长，会迫使团队重新审视一条修改从提出到兑现的整段路径。源代码、依赖、上下文、测试与批准，都可能成为被重复搬运、重复计算或重复等待的对象。

但重构的起点应是测量。先弄清一项任务真正需要什么，再决定它必须拿到哪些数据；先弄清哪些状态必须一致，再决定哪里允许并行；先弄清失败会影响谁，再决定哪里可以延后验证。没有这些前提，换一个新系统可能只是把旧瓶颈搬到更难理解的地方。

对涉及医疗流程的软件，这种区分尤其重要。代码检出更快、测试更早完成，改善的是开发交付链路，不能直接证明临床正确性、安全性或合规性。工程效率指标与医疗质量指标需要各自的验证，不能相互借名。

我更愿意把下一阶段的竞争力理解为一种系统能力：当候选方案的生成越来越便宜，团队仍能清楚知道哪些值得检验、哪些已经被验证、哪些被允许上线，以及出了问题如何退回可信状态。

代码生成的速度值得提高。更值得追踪的是，用户真正得到可靠结果的那一刻，究竟有没有提前。
