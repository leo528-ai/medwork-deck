Agent 涨了六个百分点，可能不是模型变聪明了

读 Anthropic 基础设施噪声实验：医疗科研评测必须交代运行条件

胡浩源｜京东健康 AI 副总裁，医疗专病大模型 & AI 产品线负责人

比较两个医疗科研 Agent，我们通常会关注模型、Prompt、工具和任务集，却容易把容器规格当成无关紧要的后台配置。

Anthropic 在 2026 年 2 月 5 日发布的《Quantifying infrastructure noise in agentic coding evals》提醒我们：对会写代码、装依赖、跑测试的 Agent，运行环境本身就是问题的一部分。相同模型在不同资源条件下，可能并没有参加同一场考试。

这篇文章最有价值的不是一个醒目的增分数字，而是把“基础设施更稳定”和“任务实际上变容易”区分开来。

一、先把六个百分点说清楚

原文在 Terminal-Bench 2.0 上测试了六组资源配置，从严格执行每项任务资源规格的 1x，到不设该资源上限。模型、Harness 和任务集保持相同。

从严格 1x 到不设上限，成功率提升约 6 个百分点，统计检验为 p < 0.01；基础设施错误率从 5.8% 降至 0.5%。这些数字来自 Anthropic 的编程 Agent 实验，不是医疗实验，也不代表所有系统都会得到同样收益。

更重要的是中间过程。1x 到 3x 时，基础设施错误率从 5.8% 降至 2.1%，但成功率变化并不显著，p = 0.40。原文解释，相当一部分原本被资源限制中断的任务，即使不再中断，最终仍不会成功。

从约 3x 到不设上限，成功率又上升近 4 个百分点，而基础设施错误率只额外下降 1.6 个百分点。此时资源不只是避免异常，还让 Agent 能尝试此前不可行的方案，例如安装大型依赖、启动高开销子进程或运行更占内存的测试。

二、为什么“少报错”不等于“更会做题”

容器资源有两个不同概念：预留给任务的保证资源，以及超过后触发终止的硬上限。原文发现，将两者设成同一个值，会让瞬时内存峰值也可能触发 OOM 终止。

适当增加余量，可以减少这样的偶发中断。但余量继续扩大，也会改变策略空间。一个依赖重型工具链的方案，在宽松环境中可能成功；另一个从标准库实现的轻量方案，则可能在紧约束下更有优势。

因此，不能把所有分数增长都叫作“噪声被消除”，也不能把它们都归因于“模型能力提高”。我们实际上可能同时测到了环境稳定性、资源利用策略和任务求解能力。

3x 也不是通用最佳实践。原文明确指出，合适的倍数随基准与任务分布而变化。应当进行校准，而不是把一个实验结论复制成所有医疗工作负载的默认值。

三、医疗科研 Agent 尤其容易被这些变量影响

医疗科研工作流通常不是只生成一段文字。它可能读取较大数据集，构建队列，拟合模型，执行重采样，生成图表，再填入报告模板。

在这样的链条中，内存限制会影响数据能否加载；超时预算会影响迭代次数；网络和依赖仓库状态会影响环境能否建立。同样一句“分析失败”，可能对应统计方案错误，也可能只是依赖安装时被终止。

这是本文对医疗科研场景的工程推演，而非原文的验证结论。它带来的直接要求是：失败必须分类，不能全部塞进一个模型失败率。

任务失败归因：
  环境异常：容器终止、依赖不可用、外部服务超时
  方法失败：统计方法不适用、分析假设不满足
  执行失败：代码错误、字段误用、制品不一致
  安全阻塞：权限不足、必要审批缺失

分类不是给模型“免责”。真实产品仍要统计端到端失败，只是研发归因还需要另一张表。否则，团队可能对着基础设施故障反复改 Prompt，也可能把方法错误误判为扩容即可解决。

四、评测应有一份运行条件清单

如果要判断一次模型或 Skills 更新是否带来进步，我建议固定并记录任务版本、数据快照、依赖环境、CPU 与内存的保证值和硬上限、超时、并发度，以及重试规则。

对于结果，应同时报告任务成功率、环境错误率、成本和耗时。重试后成功可以是有价值的产品指标，但要与首轮成功分开，不能把增加计算预算后的结果包装成无成本提升。

若资源条件确实发生改变，应做分层比较：同一环境下比较新旧 Agent，同一 Agent 下比较不同资源条件。这样才能回答“谁变好了”，而不是只看到总分上涨。

原文还指出，时段、集群健康、并发和网络等都可能带来影响；其中部分只是观察或尚未严格量化的因素，不能写成已有确定效应量。对我们而言，合理做法是记录这些条件，分时重复试验，并避免把细小分差解释得过于精确。

五、分数必须连同预算一起解释

资源约束不是应当彻底消除的障碍。实际业务有成本与时延要求，能在这些约束下稳定完成任务，本来就是系统能力的一部分。

因此，我更倾向于把评测分为两个视角：在固定生产预算下能否可靠交付，以及在统一、较宽松的研究条件下具备多大的能力空间。二者都合理，但不能混在一个数字里。

对于医疗应用，还必须明确：计算任务成功并不等于临床有效。资源配置可以解释代码是否运行，却不能证明研究设计合理、结论可外推或临床决策安全。后者仍需要独立验证。

这篇文章要求我们对 Benchmark 更认真，而不是否定 Benchmark。一个可用于决策的成绩，应当同时交代任务、模型、Harness、资源和验收标准。

当 Agent 的分数上涨时，先问一句“它是在什么条件下完成的”，往往比急着宣布模型变聪明了，更接近工程事实。
