ENGINEERING NOTES / OPENAI DOTS 专题

持续办事的 Agent，必须把任务、记忆和权限分开

读 OpenAI dots 官方文档：持续型 Agent 的执行边界

胡浩源｜京东健康 AI 副总裁

一个能回答问题的助手，与一个能持续承担责任的 Agent，差别不只是模型更强。前者可以在输出答案后结束，后者必须知道：事情做到哪里，下一步等什么，哪些信息值得记住，以及哪些动作仍然需要人来决定。

OpenAI 已经提供 dots 专属官方文档。它们主要说明产品机制、使用方法和权限边界，并不是完整的底层架构白皮书。阅读这些资料，最值得关注的不是拟人化外观，而是持续工作的几个边界。我的判断是：任务、记忆和权限必须分开管理，持续性才不会变成失控的惯性。

一、持续工作，不等于永远运行

官方将 dot 描述为常驻云端的 Agent：拥有自己的电脑与浏览器，用户设备关闭后仍可继续云端工作。它能够在对话之间跟进事项，决定何时暂停、何时醒来继续，也能让后台 agents 并行处理工作。[1]

这里需要区分两种连续性。固定时间重复的工作，需要保存的日程；围绕一个已委托目标，根据进展继续跟进，则不要求把每一步都改造成固定频率任务。文档还明确：连接消息来源，本身不会自动建立监控任务。[2]

从工程角度看，这意味着“持续”应当由目标与触发条件定义，而不是由进程是否一直活着定义。比如跟进一个上线问题，真正重要的是等待测试结果、识别阻塞、带回需要决策的事项，而不是每隔几分钟重复报告“仍在处理中”。这是一条设计判断，不代表官方披露了内部调度算法。

二、委派出去的任务，必须保留自己的边界

dot 可以创建独立云端线程，也可以在已连接电脑上启动 Work 或 Codex 任务，继续已有本地 Codex 任务。需要特定仓库和配置的云端编码工作，可以使用事先建立的 Codex 云环境。[2]

更关键的是，新任务获得的是为该项工作提供的指令和上下文，而不是自动继承用户与 dot 的全部历史。任务也不会因为换了一台所选电脑，就自动迁移到新环境。[2]

我把这理解为“协调者”和“执行单元”的分离：前者维持目标，后者完成有范围的工作。比如调查结算页面故障，可以把复现、修复和验证拆开，但每项任务都应有交付物与验收条件。并行不是目的，结果能够重新汇总、核验和继续推进才是目的。

官方文档特别提醒：一次运行完成，不等于请求的结果已经实现或交付。[2] 这句话值得成为企业 Agent 的验收原则。退出状态、任务完成标记与业务目标达成，不应当被混为一谈。

三、记忆不是聊天记录的无限堆积

文档区分了当前上下文、相关 ChatGPT 记忆，以及 dot 自己保存的笔记。后者记录偏好、决策和进行中的工作，与 ChatGPT 的已保存记忆相互区别，也不是所有对话的完整转录。修改 ChatGPT 的记忆设置，并不必然改变 dot 已经形成的笔记。[2]

这给产品设计提出了更高要求：记忆不仅要能写入，还要能解释来源、更新依据和适用范围。这里的可解释性要求是我的工程建议，不是对 dot 已实现能力的额外断言。

跨渠道连续性同样有边界。用户在 ChatGPT、Slack 或 Teams 联系的是同一个 dot，但可见对话仍彼此独立。信息可以帮助后续工作，却不会因此自动获得向其他受众披露的许可。[2]

因此，“知道”与“可以说”必须是两回事。私下交流的项目风险，可以帮助准备汇报；是否能把原始细节发到群里，则是另一项权限判断。长期记忆越有用，受众边界就越重要。

四、云端与本地，不只是部署位置不同

dot 的云端电脑拥有自己的文件、软件和浏览器会话，不会继承个人电脑上的登录状态。连接本地电脑后，它可以使用相应文件、应用和任务，但本地电脑需要在线，并保持 ChatGPT 应用打开。插件访问还受连接账户、权限与运行环境共同约束；本地 skills 需要已连接电脑。[3]

这些不是零散的使用限制，而是理解执行边界的线索。同一条用户请求，可能涉及不同的文件位置、会话状态和可用工具。尝试改到本地处理，不代表云端浏览器会话也随之转移。[3]

我的建议是：企业系统应把“工作在哪里运行”作为可见状态，而不是让用户猜测。遇到阻塞时，应说明缺少的是环境可用性、账户连接还是行动授权。这三者不能用一个笼统的“没有权限”掩盖。

五、技能决定怎么做，权限决定能不能做

官方技能文档将 skill 定义为包含指令、资源和可选脚本的工作流封装。系统先看到名称与描述，再在选用时加载完整的 SKILL.md；技能还可以通过插件分发。这是 ChatGPT 与 Codex 的通用扩展机制，而非 dot 独有协议。[5]

可复用工作流解决的是方法问题，不自动解决授权问题。dot 的控制文档明确：影响账户或分享信息的行动会接受自动审核，综合指令、权限、自定义规则和内置安全要求，判断能否执行、是否需要批准，或是否必须交还用户处理。要求“起草回复”，不等于授权“发送回复”。[4]

另一个容易忽视的细节是停止语义：暂停 dot 当前主任务，不会自动停止全部委派任务，也不会取消未来日程；停止工作更不会撤销已经完成的外部动作。[4]

这意味着，可靠的 Agent 不能只提供一个漂亮的“停止”按钮。它需要让用户看见执行中的任务、未来会触发的任务，以及已经产生的结果。控制权必须对应真实的工作范围。

结语：能力可以扩展，责任不能模糊

从这些公开文档，可以确认 dot 在产品层面如何组织持续跟进、任务委派、记忆和权限；不能据此反推出其未公开的 Harness 实现、后端服务结构或专用 API。

但它给我们的启发已经足够清晰：持续型 Agent 的难点，不只是更长的上下文或更多工具，而是把责任落实到可检查的边界。任务有交付，记忆有范围，环境可辨认，行动有授权。只有这样，“替人持续办事”才可能从一次演示，走向可信赖的日常工作。
