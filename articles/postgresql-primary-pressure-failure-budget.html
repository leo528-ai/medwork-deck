读请求被分散到越来越多的机器之后，一套数据库还会因为什么倒下？重读 OpenAI 的 PostgreSQL 扩容记录，我最关心的是那些没有被副本数量消除的约束：谁继续承担写入，谁负责把变更传出去，以及系统在缓存失效、某个区域不可用，或执行一次正常变更时，还剩多少可支配的能力。

Bohan Zhang 于 2026 年 1 月 22 日发表的 《Scaling PostgreSQL to power 800 million ChatGPT users》，描述了一套单主库、跨区域近 50 个读副本的 Azure PostgreSQL 部署。文中的百万级每秒查询属于整个读密集部署，“8 亿用户”也不等于同时在线人数。这是当时的工程记录，不能据标题推成单台主库的写入能力，更不能当作今天的实时容量。

文章吸引我的地方，在于它把扩容写成了一组持续收紧的约束。副本、连接池和缓存都能改善某些路径，却也会改变故障时的流量去向。

一、先辨认请求走到哪里，再谈还能扩多少

“数据库能扛多少 QPS”省略了太多前提。一次只读查询、一笔需要读后写的事务、一项后台回填，都可能被统计成数据库活动，却不能互相替换。把只读请求移到副本，并不会给主库增加一个可以提交事务的伙伴；如果事务必须在同一处读取并修改状态，那部分读取也不能仅凭“SELECT”这个词就随意迁走。

我会先画请求路径，而不是先画机器数量。入口收到请求后，是否先读缓存？未命中去哪个池？事务在哪个节点开始？后续读取有没有一致性要求？一张图若只写“应用—数据库”，最需要评估的流量转换恰好被藏起来了。两个看起来访问同一张表的接口，可能有完全不同的扩容边界。

例如，一个页面展示允许稍旧的汇总信息，另一个接口确认刚刚提交的修改。前者可以选择延迟容忍范围内的副本，后者必须检查写后读一致性、路由和可见性。这个例子是设计推演，并非 OpenAI 披露的业务接口。它说明容量规划首先需要业务契约：允许多旧、允许缺什么、什么操作必须成功，都会改变基础设施的可选方案。

因此，读扩容的成绩应当带着拓扑一起阅读。若新增副本后写延迟仍然上升，第一步未必是继续加副本；需要查清主库还在接收哪些查询，以及每次写入还触发了哪些工作。吞吐量可以汇总，约束必须沿路径拆开。

二、余量应当分给故障、维护和正在发生的业务

正常运行时的空闲能力容易被理解为浪费。对有故障切换、后台维护和快速增长的系统来说，这部分空间有明确用途。如果平时已经把所有节点安排得接近极限，一次节点退出就会把同样的工作压到更少的节点上；随后超时和重试，又可能增加原本没有的工作。

我更愿意把容量看成几类会重叠的预算，而不是一个平均 CPU 百分比。下面的划分是分析工具，不是原文提供的资源配额。

同一份余量，会被不同事件同时使用
预算用途可能消耗它的事件需要提前回答的问题
前台请求流量上涨、热点变化、查询变贵增长来自请求数量，还是每次请求做了更多工作？
故障接管副本退出、区域不可达、缓存失效转移后的请求落到哪里，剩余节点能接多少？
数据维护清理旧版本、复制追赶、统计更新维护被延后后，会不会反过来拖慢前台？
持续变更索引构建、回填、流量迁移遇到业务高峰能否暂停，恢复是否需要从头开始？

这几项不能简单相加成一个固定数字，因为它们共享 CPU、内存、I/O、网络和锁等不同资源，也不一定同时到达峰值。真正有用的是列出可信的并发场景：一个副本维护期间缓存命中率下滑，或者回填进行时业务流量上涨。资源余量必须在这些场景中仍然能发挥作用。

平均值尤其会遮住危险。一个节点平均不忙，某条连接队列却可能已经排长；一个区域整体有空闲，承担特定产品的那组实例却可能饱和。容量判断需要落到实际隔离单元上，否则总量充足也无法兑现关键请求的承诺。

三、少一次不必要的写入，收益可能沿整条链路展开

原文把减轻主库压力列为重点：卸载合适的读取，避免冗余写入，并控制后台回填。写事务内部的一部分读取仍须留在主库。

写入不能只按“改了几个业务字段”计算成本。PostgreSQL 的 HOT 文档说明，更新会产生新的行版本；满足相关列与页内空间等条件时，HOT 可以避免新增普通索引条目。因而，“每次更新都重写所有索引”是过度概括，但“很小的业务修改就一定很便宜”同样站不住。

版本产生以后还需要维护。按照 常规清理文档，已失去可见性的旧版本占用空间，需要 VACUUM 等机制处理。维护与前台共享资源，不能因为它没有出现在用户请求的同步调用栈里，就从容量账上消失。这里引用 PostgreSQL 18 解释机制，并不据此推定案例运行的服务器版本。

这让我更重视写入的业务理由。假设一个接口每次读取都更新“最近访问”字段，即使产品只需要粗粒度活跃信息，系统也可能不断制造低价值写入。能否降低精度、合并更新、改变触发条件，要由业务语义决定；这些方案不是任意延迟持久化的许可，更不能把必须可靠记录的状态一并省略。

另一个容易漏算的对象是空闲事务。客户端超时文档指出，事务内长时间空闲可能持有锁，也可能妨碍旧元组回收。表面上“没有执行 SQL”，不表示没有系统影响。超时策略应与调用链和连接池一起验证：终止会话后的错误处理、事务重试与连接恢复，都需要应用理解。

四、复杂查询的风险，取决于它能把多少工作带进主库

OpenAI 提到过涉及 12 张表的连接查询与严重事故的关联，并强调检查 ORM 生成的 SQL、简化查询。这是其负载经验，不能变成禁止所有 JOIN 的通则。

一条 SQL 的长度不是代价单位。少量高选择性数据之间的连接，和过滤不足、产生大量中间结果的连接，可能长得很像，却有不同的执行行为。业务层看到“一次数据库调用”，数据库可能已经处理了大量页面、排序或中间行。减少调用次数可以降低往返开销，却不保证总工作量更少。

将连接拆到应用层也有代价：更多往返、更大的传输量、跨查询一致性问题，以及应用内存占用。我的判断标准会是，在实际数据分布下，哪种方案的资源消耗和尾部延迟更可预测；不能只比较代码看起来是否清爽。尤其要测试热点数据和少见的大对象，平均样本往往不足以揭示最昂贵的路径。

ORM 在这里更像一个需要审查的编译过程。接口代码中增加一个关联字段，可能改变 SQL 形状，却没有明显增加代码行数。代码审查若只看业务函数，可能错过真正进入数据库的工作。对关键路径保留代表性执行计划、返回行数和资源指标，比单独规定“每个接口最多几次查询”更接近问题本身。

还要追踪请求之间的耦合。一条偶发重查询若长期占住池中连接，其他本来很便宜的请求也可能排队。优化重查询的收益不只属于它自己的延迟曲线，也可能来自被它挤占的共享资源。评估时应同时看该查询和旁路流量，而不是只截图展示一次执行变快了多少。

五、连接池能复用连接，也必须决定谁可以等待

原文使用 PgBouncer，并把应用、代理与副本的区域位置纳入部署设计。池化改善连接管理，并不直接增加数据库执行 SQL 的能力。

PgBouncer 的官方功能说明把模式差别写得很清楚：会话池、事务池和语句池，分别在不同边界归还服务器连接；语句池不支持跨多条语句的事务，事务池也需要检查会话状态的兼容性。选择更积极的复用方式，等于要求应用放弃一部分连接绑定假设，不能只改配置而不核语义。

连接数与并发工作量也不是一回事。允许更多客户端连接，可以避免连接建立失败，却可能把等待从入口搬到数据库。若下游已饱和，扩大队列通常只能容纳更多尚未完成的承诺。请求在队列里等到上游已经超时，即使最终执行成功，也未必还有用户在等待结果。

可以用一个简化的稳态算例帮助判断：若平均每秒完成 1,000 个请求、每个请求在某一池中占用连接 20 毫秒，平均在用连接约为 20。这里用的是“并发量约等于完成速率乘占用时间”的关系，假设系统稳定、统计边界一致；它不是池大小建议，也没有覆盖突发、长尾和故障接管。若占用时间翻倍，维持相同速率所需的平均并发也会翻倍。

因此，池的配置要同时回答三个问题：允许多少活跃工作、最多等多久、超过以后怎样失败。区域内就近连接可以减少不必要的往返，但不能修复慢事务。若只看连接建立耗时，而不看排队、占用和超时，池化的局部改善很容易被误读成整条请求路径的改善。

六、缓存命中率的变化，会被数据库看到成倍的流量

针对同一 key 的并发缓存未命中，原文采用锁或租约，让一个读者回源，其他读者等待填充。这处理的是同一项数据的重复回源，并非所有请求共用一把全局锁。

缓存的容量收益是有条件的。做一个完全假设的计算：入口每秒 1,000 次读取，命中率从 90% 降到 70%，数据库回源从每秒 100 次变为 300 次。入口没有增长，下游压力已经变成三倍。它只是命中率算术，不代表 OpenAI 的实测流量，也未计算重试和查询成本的差异。

如果这 300 次集中到同一热门 key，合并回源可能非常有效；如果它们来自 300 个不同冷 key，单 key 协调就不能消除这些独立读取。一个方案是否能保护主库，取决于未命中的结构。只展示全站平均命中率，会把热点同时失效和大量新数据这两种问题混在一起。

协调本身也需要失败语义。持有租约的读者超时了，其他人什么时候接手？等待者的期限是否短于用户请求期限？缓存填充成功后，原先失败的读取会不会再次发起？这些都是从机制推出的设计问题，不是原文披露的实现细节。若忽略它们，防止重复回源的控制逻辑可能变成新的等待点。

缓存故障时还需要主动选择产品行为。允许短时陈旧、返回部分结果、拒绝低优先级请求，适用于不同的数据契约。把所有未命中无条件转成数据库访问，相当于默认后者有能力接下缓存原来吸收的全部工作。这个默认值必须经过验证，不能靠平日命中率很高来替它作证。

七、故障隔离应当按可继续提供的能力来设计

案例让部分关键只读路径在主库故障时仍可由副本服务；写入仍然会失败。主库另设高可用热备。它还按优先级、产品与服务隔离负载，并为故障接管保留余量。

这里有一个值得坚持的问法：当某个依赖失效，用户还能完成什么？“数据库高可用”太笼统。读取旧记录、提交新状态、确认刚才的写入，可能是三种不同承诺。把它们拆开，才有机会让已经具备独立条件的能力继续服务，而不是让每个页面都等待同一个失效节点。

但读副本并不自动独立。应用可能先访问主库确认权限、获取路由元数据，或者在展示前完成某项同步操作。表面上只读的页面，仍可能隐藏主库依赖。需要沿完整调用链检查，不能仅凭最后一条 SQL 是 SELECT，就宣布主库故障不会影响它。

副本还涉及数据时效。PostgreSQL 的备用服务器文档说明了流复制及其延迟、故障切换等机制。允许读副本承担业务，必须把可接受的可见性差异纳入接口约定；“读得出来”与“读到了刚刚提交的状态”不是同一项保证。

隔离也有明确边界。专用读实例能减少不同产品争夺读资源，却不意味着共享写主库已经解耦。一次共同的回填或写入高峰，仍可能穿过这些边界。隔离设计需要画出剩余的共享部分，并为它们保留共同治理机制，否则局部独立容易被误认为端到端独立。

八、副本越多，传播变更这件事越值得单独计量

原文的主库直接向大量副本发送 WAL，复制扇出带来 CPU、网络与延迟压力。通过中间副本级联、进一步增加副本数量的方案，当时仍在测试，不能写成已上线成果。

这说明读扩容存在反向作用。每增加一个读节点，能够接纳更多查询，同时也增加了维护这份副本的要求。若只计入新增的读取能力，把复制支出归入一个不随规模变化的后台常数，就容易高估继续水平扩展的收益。

级联复制允许中间备用节点转发 WAL，从而改变主库承担的连接与传输拓扑。它没有让变更传播消失，而是重新分配了传播职责。讨论方案时，应该同时画正常路径和中间节点失效后的路径：下游怎样重新连接、追赶期间能否继续承担读流量、角色变化由谁控制。

我会把复制延迟当作动态信号，而不只看一个静态“很低”的数字。流量平稳时追得上，不等于写入突然增加时仍能追上；故障后恢复的节点也可能需要额外带宽。观察窗口要覆盖增长和恢复过程，才能判断平日的余量是否足够。

因而，副本数量不是孤立的成功指标。更值得比较的是：每增加一组副本，读路径得到多少收益，主库与复制链多承担多少工作，以及故障处理是否仍然可理解。拓扑复杂度也是容量成本的一部分，只是它往往在最忙、最不适合排查问题的时候才兑现。

九、限流要阻止工作进入瓶颈，而不是只统计入口人数

案例采用应用、连接池、代理与查询等多层限制，并能针对特定 query digest 阻断问题查询。重试也是需要控制的流量来源。

入口速率相同，不代表数据库负担相同。一个请求可能命中缓存，另一个可能触发昂贵查询；限制每秒请求数，并不能据此保证数据库资源消耗可控。若能定位危险的查询形状，针对性阻断可能比整项服务降速更准确，但前提是识别规则可靠、观测足够及时。

多层限制需要相互配合。应用接受了大量任务、池只允许少量执行，这本身可以是合理设计；若应用排队很久，池再排一遍，代理又有自己的期限，用户最终只会经历更长的失败。每层都配置“保护”并不等于总路径受保护，需要核对等待时间和失败如何向上传递。

重试则可能改变负载方向。下游变慢后，上游若立刻重发，数据库面对的工作会更多。退避、次数上限和总期限有助于约束它，但写操作还必须检查幂等性与提交结果不确定的情形。不能把所有超时一律当作没有执行，也不能靠一个统一重试装饰器替代业务判断。

我会要求每个降级动作说明要保住什么：是关键事务的完成率，是某类读取的时延，还是防止整个实例失去响应。目标明确以后，舍弃哪些工作才有依据。否则系统可能认真限制了低成本流量，却让少量最昂贵的任务继续穿过所有入口。

十、变更预算，应当先于上线速度被确定

原文对现有表只允许轻量变更，设置严格的 5 秒变更超时，避免表重写，并对回填限速。5 秒不是所有 DDL 或回填的完成保证；原文也未据此指定某一个 PostgreSQL 超时参数。

“只是加一个字段”描述的是需求大小，未描述执行代价。ALTER TABLE 文档表明，是否需要重写取决于具体操作、类型和默认表达式等条件；不重写也不等于不需要锁。上线评审需要知道数据库实际将执行什么，而不能只根据迁移文件的行数估计风险。

并发建索引可以避免普通建索引对写入的那种阻塞，但仍需扫描、等待并消耗 CPU 与 I/O，完成时间甚至可能更长。这里的“并发”说明与业务共存的方式，不能读成资源免费。选择变更窗口时，仍要把它放回前面的容量预算。

对大规模回填，我更看重可暂停与可恢复，而不是只看最快速度。任务应能记录进度，控制批量，在业务压力上升时降低负载，并在中断后识别已经完成的部分。这些是分析建议；具体实现依赖数据语义，尤其要检查并发写入时怎样避免把新值覆盖成旧值。

迁移还需要回滚边界。代码能回滚，不代表数据格式和约束已经恢复；停止回填，也不代表已写入的内容可以自动撤回。把结构变化、兼容代码、数据迁移和旧路径退役拆成可观察的步骤，会延长日历时间，却能减少一次动作同时改变太多条件的问题。速度应当由可承受的风险决定。

十一、保住旧系统，与停止扩大旧系统的职责可以同时进行

OpenAI 将适合分片的写密集负载迁往其他系统，既有 PostgreSQL 仍由单主承接写入，并停止在其中新增表；历史接口迁移仍在继续。这不是“单机无限扩展”的结论。

这一选择有现实含义：存量系统继续服务，并不要求所有新需求继续进入同一套边界。若一边迁移、一边让新业务不断增加依赖，迁移目标会持续后退。冻结某类新增职责，可以让工程团队逐渐把一个开放增长的问题，变成范围能够收敛的问题。

但“换成分布式数据库”并不会自动完成职责划分。首先要确定哪些数据应当一起修改、哪些查询跨越边界、失败时谁拥有最终状态。分片键如果只根据均匀分布选择，却忽略业务事务，可能把原来本地完成的判断搬成跨节点协调。这些是迁移设计的基本问题，不能从一次成功案例直接抄出答案。

存量迁移的难处也经常在接口，而不仅在数据搬运。旧客户端的行为、后台任务、报表和隐含一致性假设，都可能继续依赖原来的读写方式。需要逐步确认哪些路径已经切换、哪些仍须回退，以及双路径运行期间怎样比较结果。只验证新数据库中的行数，未必能验证业务已经迁过去。

我认为这篇案例最有价值的克制，是承认当前架构仍有明确上限。把旧系统稳定运行的能力，与为新负载选择不同结构的能力放在一起，才是一条可以持续的扩容路径。继续优化旧系统与逐步减少它的职责，并不互相抵消。

十二、衡量扩容成果，还要看系统怎样经历不正常的一天

团队报告了低两位数毫秒的客户端 p99、很低的复制延迟与五个九可用性，并称过去一年有一次 PostgreSQL SEV0 事故。这些是其部署的自述指标，未给出完整测量口径，不能扩展成整个 ChatGPT 的端到端承诺，也不能读成没有其他等级事故。

读这些结果时，我会把吞吐、时延和可用性分别追问。吞吐在哪一层计数，包含哪些请求？时延是否包含池中等待？可用性对应哪些操作与统计窗口？当系统选择拒绝低优先级工作来保住关键路径，汇总指标又怎样表达这种取舍？没有这些定义，不同团队即使报出相同数字，也未必在描述相同能力。

真正可迁移的方法，是让容量假设接受有限、可控制的验证。下面这张表是我根据前文提出的演练问题，并不是 OpenAI 公布的实验方案或结果。

验证余量时，要同时观察受保护路径与被转移的工作
受控场景重点观察它要检验的假设
部分缓存未命中增加回源速率、热点分布、等待与超时合并回源和限流能否在数据库饱和前生效
一个读节点退出剩余节点负载、重路由、关键读取隔离单元内部确实留有接管能力
低速后台变更运行前台尾延迟、锁等待、复制追赶任务能否按预设条件降速或暂停
主库暂时不可用可继续的读取、明确失败的写入、恢复行为产品降级承诺与完整调用链相符

这些演练应当有受控范围、停止条件和恢复验证。结果既用于发现瓶颈，也用于修正产品承诺：原来以为能继续读的路径，可能仍藏着一次主库访问；以为可以暂停的任务，可能还会让数据库长时间处理已经提交的工作。问题被提前暴露，余量才从图表上的空白变成真正可用的能力。

读扩容容易展示新增了多少节点，难的是知道关键路径还剩多少选择。缓存失效时可以少做什么，主库失效时还能提供什么，变更遇到高峰时怎样退让，这些决定了系统能否承受下一次增长。对于已经有复杂存量的团队，我会从一条关键读写路径开始，把正常、故障与变更三种状态画在同一张图上，再讨论该增加哪一种资源。
