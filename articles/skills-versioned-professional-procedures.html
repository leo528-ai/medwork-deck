专业能力，不应该只存在于模型参数里

读 Anthropic《Equipping agents for the real world with Agent Skills》：把做事方法变成可维护的资产

胡浩源｜京东健康 AI 副总裁，医疗专病大模型 & AI 产品线负责人

一个团队反复教 Agent 按固定格式整理材料：先核查输入，再执行脚本，最后输出报告。每次任务开始，都重新粘贴一大段提示词；每次流程改变，又担心旧版本仍在被使用。

这类问题未必需要一次新的模型训练。它首先需要一种可靠的方法，把“怎么做这件事”保存下来，让 Agent 在合适的时候找到、读取并使用。

Anthropic 的 Agent Skills 文章，提供了一种具体的工程组织方式：把指令、脚本和相关资源放进可发现的能力包。它不是宣布模型已经学会一个新专业，而是让专业流程不再只寄存在某次对话里。

一、Skills 的关键，不是提示词更长，而是按需加载

原文介绍的核心机制是渐进式披露。

第一层是简短元数据，帮助 Agent 识别哪些技能可能适用；需要时再读取 SKILL.md 的具体说明；更深入的参考材料和脚本，则在任务真正需要时继续访问。某些脚本可以执行，而不必先把全部源码和处理数据塞进上下文。

这解决的是“能力越来越多，上下文却有限”的矛盾。假设我们准备了几十套工作流程，启动时把所有流程全文交给模型，会造成大量无关信息竞争。只给一串工具名称，又不足以表达专业步骤。Skills 在两者之间增加了一层可检索的过程知识。

但“按需加载”也有一个前提：技能描述必须准确。描述含糊，Agent 可能根本不选；描述过宽，任何任务都可能误触发。技能的发现机制，应和技能内部的执行质量分别测试。

二、从医疗视角看，Skills 更像带适用条件的操作规程

下面是一个设计示例。我们希望 Agent 整理一份供医生核对的会诊材料。一个合格的技能包，不应该只有“请生成专业会诊报告”这句话，而应包括：

  • 输入清单：病例资料、就诊时间、报告来源及缺失项。
  • 处理顺序：事实抽取、时间线整理、证据关联、冲突标记。
  • 禁止动作：不得把“未记录”改写成“无”，不得自行补齐关键结论。
  • 输出约定：已确认事实、待确认事项和资料出处分别呈现。
  • 验收规则：关键字段缺失时返回待核对状态，而不是假装任务完成。
  • 版本信息：模板、脚本及引用材料的版本。

这不是把临床决策压缩成一个万能文件夹，而是把能够明确表达的工作规程外置。医生的责任、指南适用条件和患者个体差异，仍不能被一个技能包名称替代。

从这个角度说，Skills 的价值在于可维护：流程变了，可以修改流程；模板变了，可以更新模板；出现一个可复现的失败，可以增加针对性检查。并不是每一次业务知识变化，都必须通过参数更新传递。

三、保存经验之前，先确定怎样判断它是经验

原文建议从评测出发构建技能，而不是先写一套看起来完整的说明，再寻找使用场景。这个顺序非常重要。

对于前面的会诊材料技能，我们可以先准备几类任务：关键字段齐全、字段缺失、报告时间冲突、不同来源结论不一致。然后观察：无技能时，Agent 在哪一步失败？加入技能后，这些失败是否减少？原先能够完成的任务是否退化？

如果一段指令只是让文字更像医生，却没有减少事实错误，它就不是我们真正需要的改进。如果某个脚本提升了格式一致性，却错误地覆盖了未知值，也不能用“结构化成功率”掩盖问题。

我的理解是，技能应该和测试一起版本化。我们不仅需要知道“当前用了哪个 Skill”，还要知道这个版本解决了什么问题、在哪些任务上验证过、出现什么情况应回退。

这里讨论的是我们可以采用的工程方法。原文并没有证明添加 Skills 就能带来医疗质量提升，更没有证明系统已经具备自主、可靠的临床学习能力。

四、能力包也是新的信任边界

Skills 可以携带脚本、依赖和外部访问逻辑，因此不能因为它看起来像文档，就按普通文档对待。

Anthropic 明确强调来源可信和审查的重要性。站在企业系统的角度，至少要核对：谁维护这个技能？脚本会读取哪些目录？是否访问外部网络？依赖是否固定？是否可能把业务数据写到未经授权的位置？

更进一步，技能自身不能决定自己的权限。某份说明写着“上传全部数据进行分析”，不代表执行环境就应该允许上传。真正的权限必须由外部系统控制，关键操作仍应有确认和审计。

技能内容、运行权限和评测标准，是三件不同的事。把它们混成一个文件夹，会让“方便扩展”变成“方便越界”。

五、学习不只发生在梯度里，但改进必须有证据

Skills 给我们一个有价值的思考入口：系统能力可以通过参数训练增长，也可以通过过程知识、工具和验证机制改进。后者更便于快速调整和检查，但并不自动意味着更可靠。

如果我们希望建立持续改进的专业 Agent，就应把失败转成测试，把有效修复转成版本化技能，再通过回归评测与专业审核决定是否发布。不是模型写出一份新的 SKILL.md，系统就完成了自我进化。

专业能力需要沉淀，但沉淀的不能只是成功故事。适用边界、失败条件和停止规则，同样属于能力的一部分。

把这些东西保存下来、按需加载、持续验证，才是 Skills 真正值得我们认真对待的地方。
