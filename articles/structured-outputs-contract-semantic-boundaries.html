格式正确之后，谁来保证事情做对

重读 OpenAI Structured Outputs：约束解码解决了哪一层可靠性，证据、业务校验和执行授权又该留在哪里。

一、一份可以解析的结果，未必可以交付

设想一个文档助手要从一份会议纪要里提取负责人和截止日期。它返回了合法的 JSON，字段齐全，类型正确，程序也顺利将它存进数据库。可是纪要里说的是“下次会议前讨论”，系统却写进了一个确定的日期。机器之间的交接没有出错，工作本身已经错了。

这类问题容易被一个过于宽泛的词遮住：可靠。接口可靠、事实可靠、决策可靠、执行可靠，并不是同一件事。当我们说模型输出已经“百分之百符合要求”，首先要追问：符合的是哪一份要求？检查的是括号和字段，还是材料里的事实，或者外部系统里的结果？

OpenAI 在 2024 年 8 月 6 日发布的 Structured Outputs，提供了一个值得认真拆开的工程案例。本文重读这篇历史技术文章，不把当年的接口、价格和模型列表当成今天的接入指南。除明确标注的原文事实外，下面的工作流、字段设计、反例和验收方法均是我的工程分析，不是 OpenAI 的产品承诺。

二、把一种失败从概率问题变成约束问题

原文区分了两件事：生成合法 JSON，与满足开发者指定的 JSON Schema。其方法结合模型训练和约束解码；当时复杂 schema 跟随评测中，gpt-4o-2024-08-06 模型本身达到 93%，加入严格约束后报告为 100%。这里测的是结构符合度，不是内容真实性。

原文描述的机制是把 schema 转为上下文无关文法，预处理并缓存；生成每个 token 后，依据已有前缀和文法重新计算允许的后续 token，将不合法选项屏蔽。递归结构是采用文法而不只依赖有限状态方法的重要理由。新 schema 预处理带来首次延迟，支持范围也不是全部 JSON Schema。拒绝或生成中断需要单独处理；对象里的值仍可能错误。

这段机制给我的启发，不是“提示词终于可以省掉了”，而是把可穷举的格式要求从模型的自觉中拿出来。提示词要求模型记得某条规则；约束机制直接收窄可生成的空间。两者承担的责任不同，不能只用同一套提示词写得更长来替代。

可以把它想成一个有轨道的填表过程。轨道规定哪些格子存在、哪些类型可以进入，却不会自动知道原始文件究竟写了什么。如果日期栏仅允许预先给定的日期枚举，把姓名填进去可以在接口层拦住；如果只规定它是字符串，则连这一步也不能保证；把另一个人的日期填进正确的日期栏，仍然需要证据层检查。这个比喻是我的解释，不是对具体内部实现的额外披露。

三、schema 应该表达未知，而不是强迫填满

很多抽取系统的问题并不在解码器，而在字段的设计。需求文档写“必须给出截止日期”，工程师把日期定义成必填字符串，模型最终交出一个日期，产品便认为任务完成。但原文可能根本没有日期。此时系统把“字段必须存在”悄悄变成了“事实必须存在”。

我会先区分三个状态：材料明确给出；能够按明确规则推导；材料不足。第三种不是失败的边角料，而是业务正常状态。字段应该允许保存未知，同时记录缺少什么。至于具体用可空值、状态字段还是不同结果类型，要看所用接口支持的 schema 子集以及下游程序的契约，不能照搬一个示例就宣称可直接上线。

以虚构会议纪要为例，可以在业务对象中保留 raw_text、normalized_value、evidence_ref 和 resolution_status。raw_text 保存原句，normalized_value 仅在证据充分时填写，evidence_ref 指向能被重新读取的位置，resolution_status 区分直接提取、规则推导和待澄清。它们是业务设计建议，不是一份经过 API 验证的 schema。

真正有用的设计问题是：原句变更后，我们能不能知道哪个字段需要重算？如果“周五前”来自上一版纪要，而负责人来自最新版本，即使两个字段分别有出处，合起来仍可能是一个从未存在过的任务。证据必须有版本，不只是一个看起来像引用的字符串。

未知也不能成为万能出口。对材料已经明确给出的信息，如果系统总写“待澄清”，结构仍然合法，产品却把工作退回给了用户。因此，抽取的验收既要检查无证据的确定值，也要检查有证据却遗漏的值。

四、业务校验要站在生成器外面

下一层是关系约束。开始日期不能晚于结束日期；合计应与分项一致；引用编号必须实际存在；同一任务不能同时处于互斥状态。这些条件里，有些可以直接用代码检查，有些需要查阅外部权威状态，有些只能由具备专业资格的人判断。

我倾向于把检查器和生成器分开部署、分开记录结果。不是因为模型不能帮助校验，而是因为“模型说自己检查过”无法构成独立证据。如果一个输出声称 checked=true，却没有对应检查器的版本、输入和结果，这个字段只是另一句自然语言的变体。

对于证据引用，最低限度的检查不是字段非空，而是引用能解析、目标存在、版本一致、引用范围确实包含该事实。最后一项往往比前几项困难。系统可以自动核对数字是否出现，但数字出现在否定句、历史记录或另一个对象下面时，简单匹配并不够。

我会将自动通过、自动拒绝和需要复核分开，而不是让所有异常都走一次“请模型修复”。缺了一个可确定的字段，可以要求重提取；证据冲突，应暴露冲突；资料不存在，继续生成不能补出资料。重试动作必须针对错误类别，否则只是用更多次调用换来一次看似完整的表格。

这些安排并不证明任何医疗系统具备临床安全性。若涉及真实诊疗用途，还需要对应场景验证、专业审核、隐私与合规控制；结构化输出不能替代这些要求。本文的文档例子不包含患者数据，也不构成诊疗建议。

五、合法参数与获准执行之间，还隔着一道门

结构化结果进入工具链后，风险会再变一次。生成一个计划，与执行这个计划不是同一个行为。一个字段可以合法地写着“发送”，但用户可能只要求“起草”；一个收件人地址类型正确，也可能不是用户授权的收件人。

因此，执行器不应该把模型输出中的 authorized=true 当成许可。授权需要从可信的用户指令与权限系统获得，核对动作、对象、范围和有效时间。模型可以提出动作建议，但不能通过自己生成一个字段扩大自己的权限。

我会把一次有副作用的操作拆为候选结果、已校验结果、待执行请求和外部完成记录。前三种都还不是完成。只有外部系统确认了预期状态，才能把任务标成成功。对于发布内容，要核验公开页面；对于写文件，要核验目标位置和内容；对于发送信息，要核验实际收件人和发送结果。

网络超时尤其考验这种分层。如果提交之后没有收到响应，不能立即认为“没有发生”并重发。应先查状态，并在业务允许时使用幂等标识。格式约束减少了输入的不确定性，却不会消除外部系统的失败、重复和部分成功。

这也是我不赞成把一大串工作压成一个“万能 JSON”的原因。把所有可能动作都装在一个对象里，并不等于它们共享一个授权边界。需要独立确认的动作，仍然应该有独立的状态与凭据。

六、验收时，把漂亮的总分拆成四张账

如果我负责这类能力的验收，不会只看 JSON 解析成功率。第一张账是协议：响应是否完整、是否拒绝、结构是否符合约定。第二张账是信息：字段是否正确、完整、与证据一致。第三张账是决策：面对缺失、冲突和歧义，系统是否采取合适的下一步。第四张账是执行：在授权范围内，外部结果是否真正发生。

这四张账不能互相抵消。结构失败后，后面的字段正确率可能根本没有评测机会；仅对成功解析的样本统计事实正确率，会把最难的样本排除在外。报表应同时给出每一层的分母和被排除的原因，并保留端到端任务完成率。

测试材料也应该成组构造。第一份材料写出明确日期；第二份删掉日期；第三份出现两个版本的日期；第四份保留日期却更换任务对象。这些都是自拟测试，不是原文实验。它们能够检查系统究竟在使用证据，还是在习惯性填表。

另一个维度是运行条件。新 schema 与已使用过的 schema 分开统计延迟，完整响应与中断响应分开统计，结构变化前后保留回放样本。某个平均耗时变低，可能只是测试里复用了更多已处理的结构，并不表示所有请求都变快。

若业务允许重试，应记录首次通过、重试后通过和最终未完成，同时统计调用成本。不能用无限重试后的漂亮结果与另一个版本的单次结果比较。重试预算、工具权限、材料版本和检查器版本，都属于实验条件。

最后，检查器本身也需要测试。给它一份字段齐全但事实错误的对象、一份事实正确但引用过期的对象，以及一份明确标注未知的对象。如果这些结果都被判成相同状态，问题可能不在模型，而在我们尚未定义清楚“通过”。

七、确定性应该被放在有能力负责的地方

我从这篇文章里得到的工程判断是：不要要求同一层系统为所有事情负责。可形式化的结构交给约束机制；可复现的关系交给代码；来源和版本交给证据管理；执行权限交给可信的授权边界；高风险判断交给相应的专业流程。

这并不意味着系统越分层越好。每加一层都会带来延迟、维护和故障诊断成本。分层的价值在于发生错误时，能够回答三个问题：是哪一项承诺没有满足，谁负责检查，以及怎样恢复而不制造更大副作用。没有这些答案，更多字段和更多节点只是更复杂的外观。

Structured Outputs 值得重视，因为它让一种明确的约束不必完全依赖生成模型的自觉。但把这种进步理解为“输出已经可信”，反而会浪费它的价值。协议层越稳定，团队越应该把注意力移向过去被格式错误遮住的事实与执行问题。

一份结果终于可以被程序读懂，是重要的起点。它是否值得被相信、是否允许被执行、是否真的完成了用户的事情，仍然需要各自的证据。
