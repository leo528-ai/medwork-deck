有限判断何时值得委派：Jev 的一组集成实验

胡浩源｜京东健康 AI 副总裁，医疗专病大模型 & AI 产品线负责人

依据 2026 年 9 月 22 日接入报告整理

  3. 三、“需复核”不是失败，完整性也不等于正确性

一次单标签分类对照给出了清晰的效率收益；小任务、多标签质量和自主委派测试，则划出了不能忽略的边界。下面讨论的都是 2026 年 9 月 22 日接入报告中的内部工程结果，不是外部排行榜，也不是临床有效性评估。

给 Agent 增加一个工具，不等于它会主动使用；让一段任务跑得更快，也不等于整个系统更便宜、更准确。Jev 接入 MedWork 的这轮结果，恰好把这些问题分开了。

最直观的结果来自同一附件的 768 条评价分类：禁用 jev_batch 时，从用户发送请求到助手完成交付需要 46.027 秒；明确使用时需要 16.852 秒，耗时降低 63.4%，约为 2.73 倍速度。两组都交付了 768 个唯一 ID，按既有样本答案核对，正确数由 744 条变为 757 条。

但这不是 768 条独立真实客户评价的线上试验。输入是由 32 种语义模式扩展而来的测试记录，端到端对照只各运行了一次。能够成立的结论，是在这份输入、这套任务要求和这次执行路径下，专用批处理工具减少了交付等待；不能据此推导所有分类任务的平均收益。

更有价值的部分，是把这次成功与另外几组并不理想的结果放在一起看：什么工作适合交出去，什么工作不值得交，交出去以后又该验收什么。

一、这次接入的 Jev，承担的是有限判断与连续执行

报告使用的是 Jev 1.13.0 接口，交付了两个工具：jev_browser 和 jev_batch。报告没有解释 Jev 的英文全称，也未披露底层模型架构和训练细节。这里沿用其名称，只讨论报告能够支持的接口行为与接入结果。

它的接入方式不是让 Jev 给出建议，再由主模型把每一步建议翻译成工具调用。主 Agent 先提供目标、规则、必要输入、权限和验收条件；工具在一次外层调用中完成多步操作或多批记录；主 Agent 最后核验目标并组织交付。

两条路径各自承担不同的工作：

  • 浏览器路径：观察真实页面，在有限的 DOM 候选动作中判断，执行后再观察。适用工作包括连续点击、跳转、筛选、滚动，以及填入调用方已经提供的准确文本。
  • 批处理路径：读取选定文本字段，按有限标签集合判断，再由程序完成 ID 映射、数量统计、明细和分组文件输出。

这次接入复用了既有工具执行环境，收益主要来自减少主 Agent 的重复判断与执行往返。

这也决定了责任边界。浏览器操作完成不等于业务目标完成，最终验收仍由主 Agent 负责；批处理返回完整文件，也不等于分类质量已经达到所有业务的要求。

二、768 条分类：端到端时间降了，任务要求没有缩水

这组对照的要求相当具体：只读取每条记录的 text，以 id 作为唯一标识，按照本人当前的主要诉求，分为配送问题、商品问题、退款售后、好评、需复核五类。多个未解决问题没有主次，或者信息不足时，应该输出“需复核”。交付物不仅是标签，还包括各类数量、完整逐条结果和分组文件。

两次请求的目标一致，主要差别是明确使用或禁止使用 jev_batch；两次均未激活 Skill，因此比较的是通用主 Agent 路径，而不是两个不同的业务 Skill。

耗时减少了 29.175 秒。主模型累计输入减少 67.4%，输出也明显缩短。正确数增加 13 条，对应正确率提高约 1.69 个百分点，而不是“提高 13%”。

两条执行路径的差别，比单独看速度更能说明问题。

禁用 Jev 时，主 Agent 通过 5 次终端调用完成数据读取、推理、生成分类映射脚本、映射与核验。使用 Jev 时，外层是 1 次终端调用和 1 次 Jev 批处理，后者内部实际发出了 24 个请求。报告记录的 Jev 工具内部用时为 3.480 秒，768 条全部处理，失败批次和未处理项都为零。

3.480 秒是工具内部时间，16.852 秒才是这次用户实际等待的端到端时间。不能用前者去与基线的 46.027 秒相除，制造一个更大的“提速倍数”。同样，外层的一次批处理调用，也不意味着底层只有一次模型请求。

这次收益与执行路径的变化相符：把文件交给专用工具完成判断、统计和落盘，减少了主模型反复阅读大段数据、生成映射脚本和组织长输出的工作。不过，报告没有提供逐阶段耗时拆分，不能进一步声称每一项机制分别贡献了多少秒。

还有一个容易混淆的细节：工具支持对指定字段完全相同的记录进行精确去重，但这次 768 条记录实际全部经过判断，没有发生精确去重。因此，这次提速不能归因于“把重复记录省掉了”。

三、“需复核”不是失败，完整性也不等于正确性

报告中的两张会话结果截图，给出了分类数量：

实验数据表 2：输出标签、禁用 Jev、使用 Jev
输出标签禁用 Jev使用 Jev
配送问题120120
商品问题144135
退款售后144144
好评168142
需复核192227
合计768768

使用 Jev 的结果中，有 227 条被分到“需复核”，约占 29.6%。这不是 227 条执行失败，也不是 227 条漏判：按照任务定义，在信息不足或无法确定主要诉求时，“需复核”本身就是合法的目标标签。报告同时记录了零未处理项，两者并不冲突。

反过来，保留了全部 ID、五类数量相加等于 768，只能说明交付完整，不能证明语义判断正确。正确率还需要和预设答案比较。

这里至少要区分三件事：

  1. 执行有没有完成：有没有失败批次、未处理项。
  2. 数据有没有交齐：是否存在漏行、重复 ID，统计是否与明细一致。
  3. 判断有没有做对：标签是否符合任务口径和参考答案。

这次对照的前两项都通过了，第三项并非满分：Jev 仍有 11 条与既有答案不一致，禁用路径有 24 条不一致。

“需复核”增加 35 条，与正确数增加 13 条，也不能直接解释成同一件事。报告没有提供逐条预测、真实标签和混淆矩阵，无法判断这 35 条具体从哪些类别转来，哪些改判是正确的。不能仅凭分类数量就宣称某种“更谨慎的策略”导致了质量提升。

对实际部署而言，这组结果说明的是：验收应同时看完成情况、交付完整性和标签质量，而不是只看一个正确率，或者只看文件是否成功生成。

四、主模型 Token 减少，不等于总费用已经下降

这次对照中，主模型输入从 234,022 Token 降到 76,270 Token，是一个明确的路径变化指标。但使用 Jev 的一侧，还有额外用量：

实验数据表 3：Jev 额外用量、报告记录
Jev 额外用量报告记录
输入166,157 Token
输出44,508 Token

因此，“主模型输入减少 67.4%”可以直接引用；“总 Token 减少 67.4%”不可以；“费用降低 67.4%”更没有依据。

不同调用路径的计费单价、缓存折扣、输入输出计价和其他费用，都不能从主模型 Token 一项里推导出来。报告明确将实际费用留待账单核算，也没有提供足以进行费用对照的完整计价条件。

这里适合保留两个独立结论：这次任务的端到端延迟降低了，主模型承担的输入输出负担减轻了。系统总成本是否更低，仍是待核算的问题。

把延迟、主模型占用和费用拆开，反而能更准确地判断工具的工程价值。有的路径可能以额外专用调用换取更短等待，有的路径可能同时节省费用；只有完整账单才能回答属于哪一种。

五、浏览器：执行器有效，自动委派还没有成立

浏览器部分的最新受控回归是一个七动作任务，明确启用 Jev，只有一对运行：

耗时11.552 秒8.451 秒
主模型调用次数19 次4 次
真实页面验收通过通过

这一对运行中，耗时降低 26.8%，主模型调用数由 19 次降到 4 次。它证明了在这个受控任务里，连续操作可以被放进专用执行路径，且最终页面状态通过了验收。

但另一组结果必须同时公开：浏览器自然选择测试共 33 次，主 Agent 一次也没有委派给 Jev。

“工具执行时有收益”和“Agent 会在合适的时候调用工具”，是两道不同的门槛。受控回归支持前者，自然选择测试没有支持后者。不能把明确启用条件下的 19 → 4 次调用，写成系统默认行为已经自动优化。

在报告所述配置中，浏览器工具的可见性也有条件。jev_browser 不是默认工具，需要由 browser-use Skill 声明，并依赖 Desktop 内置浏览器；纯云端环境没有该浏览器时不可用。因此，接入报告提出的下一步重点是完善 Skill 委派，让适合的流程明确交出整段任务，而不是期待工具注册后就自然获得调用。

执行边界并没有因为“连续”而取消。按报告描述，工具基于真实 DOM 候选执行，并校验页面快照；不通过任意脚本或猜测坐标绕过边界；缺少必需输入时停止；必要时可要求观察到正文，避免把标题当成已经读过的内容。既有权限和操作安全检查保持不变。

这些是报告描述的实现约束，不是独立安全审计的结论。一两步直达操作、需要看图推理、输入不完整或高风险的任务，也不在其默认适用范围内。

六、两个反例：更小的任务更慢，多标签更快但未达质量线

如果只展示 768 条单标签任务，这次接入很容易被误读成“分类全部交给 Jev”。另外两组评测说明，这样的默认策略并不合适。

240 条多标签：约 1.61 倍速度，但两组都未达标

这组输入是 24 种语义模式加流水号形成的 240 条记录，两种条件各运行 3 次。报告说明，多次运行采用中位数汇总。

实验数据表 5：指标、不用 Jev、使用 Jev
指标不用 Jev使用 Jev
耗时14.173 秒8.812 秒
报告所列正确率91.81%91.67%

速度约提高到 1.61 倍，但 Jev 的正确率没有提高，反而低了 0.14 个百分点；两组都低于报告设定的 95% 质量线。

因此，这组结果不能作为“多标签任务可以放心委派”的证据。它只说明，在该测试里更快的路径仍未满足质量要求。若质量门槛不可让步，延迟收益不能替代达标。

报告也没有给出多标签正确率的详细计分定义、逐次运行明细或逐标签指标。这里保留其原始指标，不将其擅自解释成完全匹配率、微平均 F1 或其他常见评测口径。

24 条和 12 条小任务：开放工具的条件更慢

在小型内联任务中，主 Agent 自主选择是否调用 Jev；工具可用，并不意味着每轮都实际使用。两类任务同样各运行 3 次：

这不是对每次实际 Jev 调用开销的纯测量，因为有些轮次没有调用工具。能够直接说的是：在这两类小任务和这组自主选择设置下，开放工具的路径没有获得效率收益，耗时反而更高。

工具调用和交接并非免费。材料很少时，主模型直接完成可能更合适。不过，这几组结果不足以给出一个通用的条数阈值，例如“超过 100 条一定更快”。文本长度、标签复杂度、输出要求和执行环境都可能影响分界点，报告没有进行这样的阈值扫描。

七、从这轮结果得到的，是一条有条件的委派规则

把正面结果与反例放在一起，当前更合理的使用方式并不复杂：

实验数据表 7：工具、优先考虑、不应默认使用
工具优先考虑不应默认使用
jev_batch已有较大批量独立文本、有限标签、边界明确，且结果需要直接统计和分组少量简单文本、确定性计算、复杂多标签、高风险医学判断
jev_browser目标清晰、多屏多对象、连续常规操作，并由适合的 Skill 明确委派一两步直达、看图推理、必需输入缺失、高风险操作

在本次接入实现中，批处理工具可用于云端和本地环境，默认对主 Agent 可见，也可由 Skill 排除。它支持工作空间 JSON/JSONL 或内联记录、单标签或多标签以及共享业务背景；但“接口支持”不等于“每种设置都已经证明适用”。

其工程实现中还有两项值得保留的边界：只发送指定文本字段，精确相同字段只判断一次，再还原全部 ID 和原始顺序，不做语义近似合并；失败时保留未处理子集供续跑，不重跑已完成项。这些机制有助于控制数据流与重复执行，但本轮报告没有给出失败恢复专项测试，不能把支持能力写成已经量化验证的收益。

报告还说明，合法判断会直接执行，不因概率低就交回主模型逐项重判。这减少了“专用工具判断一遍，主模型再判断一遍”的重复路径，却不意味着低置信结果天然可靠。有限标签的设计、允许“需复核”的业务口径、适用范围限制和结果抽检，仍然重要。

对于医疗健康场景尤其如此。这轮分类输入是评价测试记录，浏览器评测是工程操作任务；它们没有验证诊断、处方或其他高风险医学判断。不能从评价分类的 98.57% 正确率，跨越到临床准确性或医疗安全性的结论。

八、下一轮需要补的，不只是更多速度数字

本次报告足以支持一条有边界的工程判断：在一部分连续操作和大批量有限标签任务中，主 Agent 不必亲自承担每一步重复判断与执行，专用路径可以减少端到端等待。

要把它变成稳定的默认策略，还需要补齐几类证据：

  • 重复性：768 条端到端任务和七动作浏览器回归目前都只有一对运行。需要多次、交错顺序的对照，观察波动，而不是把单次倍数当成长期均值。
  • 样本覆盖：768 条来自 32 种语义模式，240 条来自 24 种语义模式。记录数不等于独立语义场景数，需要更广的任务分布验证。
  • 质量定位：提供逐条预测、参考答案、错误类型和多标签计分定义，才能知道哪些标签受益、哪些边界仍然容易误判。
  • 自动委派：既测“明确交给工具后能否完成”，也测“无需提示时是否会在合适任务上调用”，并观察不该调用时是否避免调用。
  • 完整成本：把主模型和 Jev 的实际账单放在同一个任务口径下核算，而不是用某一路 Token 的减少代替总费用变化。

这些是从现有证据缺口推导出的下一轮验证建议，不是已经完成的结果。

这轮接入最值得保留的，不是一个脱离条件的“2.73 倍”，而是任务拆分后的判断标准：大批量、有限判断、完整交付，可以优先考虑委派；任务很小、质量未达标、边界不清，就不要为了使用工具而使用工具。

让主 Agent 更专注于规划和交付，前提不是它做得越少越好，而是交出去的工作有清楚的输入、执行边界和验收标准。Jev 在部分任务上已经显示了这条路径的收益，下一步要解决的是何时交、能否稳定交对，以及交付之后如何证明结果可信。

资料与口径

本文依据《MedWork · Jev 工具接入汇报》（2026 年 9 月 22 日）的正文、表格和两张内嵌会话结果截图整理。数值为报告所列的内部工程评测结果，未作独立复跑或第三方验证；文中的百分比与倍数按原始数值计算并四舍五入。

报告在受控评测部分将对照模型记为 Qwen 3.8 27B。现有材料未提供完整模型配置、采样参数、硬件、并发、缓存和网络条件，亦未为 768 条端到端对照单独列出完整配置，本文不据此补写缺失设置。原报告引用的评测明细、代码及样本文件未随当前材料展开，因此本文不把这些引用等同于已逐项核验的证据。

为便于公开阅读，本文未保留本地会话地址、内部会话标识、开发目录和原始界面截图；使用的是匿名汇总结果。
