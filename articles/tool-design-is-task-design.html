工具接上了，Agent 为什么还是不会用？

读 Anthropic《Writing effective tools for agents — with agents》：工具设计首先是任务设计

胡浩源｜京东健康 AI 副总裁

给 Agent 接入几十个接口，并不等于给它增加几十项可靠能力。

一个容易被忽略的区别是：传统 API 面向确定的程序调用方，Agent 工具却面向一个需要在上下文中理解意图、选择动作、解释返回值的模型。后端接口设计得正确，模型仍可能选错工具、填错参数，或者拿到一大段结果后看漏真正重要的信息。

Anthropic 这篇文章讨论的不是“如何让模型记住更多工具”，而是如何让工具本身更容易被正确使用。我认为，其中最值得带到专业 Agent 的判断是：不要按照后台系统的组织方式暴露工具，要按照任务的完成方式设计工具。

一、把数据库接口交给模型，不等于把业务能力交给模型

原文用联系人查询等例子说明，直接提供 list_contacts 一类宽泛接口，可能把筛选负担全部推给模型；面向具体目标的 search_contacts，则更接近用户真正想完成的动作。

这里的重点不是搜索一定优于列表，而是一个工具调用究竟减少了多少不必要的推理。用户要找某个人的联系方式，Agent 不该先读取整个通讯录，再在长上下文中逐条比较。调用方已经知道的条件，应尽可能变成明确参数，由确定性的程序处理。

这对医疗场景尤其重要。假设我们设计一个病例准备助手，用户需要的是“找到这次会诊所需、仍然缺失的关键检查”，而不是“调用某个表的查询接口”。如果工具只返回几十份报告，模型就得同时解决时间归属、项目名称映射、重复记录和是否缺项等问题。链路越长，出错位置越多。

一个更好的设计起点是：工具先把患者、就诊事件、时间范围与报告状态说清楚，再返回与当前任务相关的结构化记录。注意，这不意味着把临床判断偷偷塞进工具。数据过滤可以程序化；某项检查是否足够支持临床决策，仍须明确专业规则和审核责任。

二、工具返回值，本身就是下一步决策的输入界面

Anthropic 特别强调，返回值不应充满难以解释的内部标识符，应提供模型能理解、能继续操作的信息；同时可以区分简洁和详细输出，避免每次调用都占满上下文。

很多团队只评审函数签名，不评审返回内容。这相当于认真设计了门把手，却没管门后面是什么。

面向 Agent 的返回值至少要回答三个问题：找到了什么？哪些部分尚不确定？下一步允许怎样继续？“查询成功”只是程序状态，不是任务状态。空结果也不能统一解释成“没有这项检查”：它可能意味着检索范围不对、数据尚未同步，或者当前身份没有权限。

下面是一个设计示例，并非生产接口：

{
  "status": "partial",
  "encounter_id": "visit_123",
  "records": [
    {"type": "lab_report", "time": "2026-10-01", "source_ref": "report_456"}
  ],
  "missing_fields": ["specimen_time"],
  "next_action": "request_source_review"
}

它没有替模型给出诊断，但把“已获得记录”与“尚未具备判断条件”分开了。模型可以据此请求核对，而不是在一段顺畅的自然语言中补齐事实。

原文对结果截断和错误信息的建议，也应这样理解：不要仅告诉 Agent 失败了，还要给它可执行的修正方向。例如时间窗口过大，应明确提示缩小范围，而不是返回一个没有上下文的错误码。

三、少调用几次，不是唯一的优化目标

工具可以更粗，也可以更细。粗粒度工具减少调用次数，却可能隐藏中间状态；细粒度工具便于核查，却增加编排负担。不存在“工具越少越好”的普遍答案。

真正应该比较的是：在相同任务集上，哪种接口更容易获得正确结果、留下足够证据，并在异常时安全停止？原文提出通过真实任务评测迭代工具，并保留独立评测集。它也提醒，不要因为一条轨迹不同于预设路径，就把成功任务判成失败。

这对我们的启发是，工具评测应把“结果错误”和“路径不同”分开。获取同一份有效报告，走了两种授权检索路径，不一定有优劣；拿到另一位患者的报告，即使调用顺序完全符合脚本，也必须失败。

对于有外部影响的操作，还需要另外定义权限、幂等性、预览与确认。一个描述清晰的工具，不会因此自动变得安全；模型理解接口，与系统限制操作，是两件事。

四、工具工程的终点不是接通，而是降低歧义

这篇文章没有证明某种接口设计可以消除医疗风险，也没有给出适用于所有业务的统一工具粒度。它提供的是一种扎实的工程方法：先围绕任务设计工具，再用实际失败来修正工具，而不是把模型的每一次误用都归因于“能力不够”。

对于专业 Agent，我更愿意把工具视为一份可执行的业务契约：什么输入才有效，什么输出有依据，什么情况下必须停下来。

只有这些边界清楚，模型的聪明才不会被消耗在猜接口、猜字段、猜系统状态上。工具不是模型能力之外的附件。工具如何设计，决定了模型能力以什么方式进入真实业务。

原文：Anthropic，2025 年 9 月 11 日。本文为独立技术解读，医疗示例为设计推演，不是原文实验结论。
